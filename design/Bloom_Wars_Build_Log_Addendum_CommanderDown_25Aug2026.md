## Addendum, 25 Aug 2026 (same day, later still): the real commander-down fix — Rourke reaching 0 HP now actually ends the mission attempt

Maxime, picking up right where the doc-staleness incident (batch 7, above) left off: "sync everthing togheter and build in the mc permadeath bring mission to its end. restart from mission bried. (I would do from scratch, but thats a mode for later)." Two explicit asks, both closed this pass — sync the drifted docs (Master Index, this build log, and the Independent Campaign doc's own status paragraphs all confirmed current against the Project as of this addendum) and fix the actual bug: Rourke going to 0 HP has to end the mission attempt and return the player to the briefing screen to retry the same mission — explicitly not a full from-scratch campaign restart, which Maxime named directly as its own later mode, not this one.

**What was actually live before this pass, confirmed by reading the code rather than assuming the design doc's own rule was already built.** `engine/campaignState.ts`'s `evaluatePermadeathCheck` has always had a `PilotRecord.exemptFromPermadeath` branch (`pilot_rourke`'s own flag, `data/campaignAmaranth.ts`) — but what it actually did was return `{ permanent: false, reason: "... is exempt from permadeath — always a standard restock" }`. `Mission.handleDowned()` (`engine/mission.ts`) called that function unconditionally for every downed player pilot and never branched on the result beyond the permadeath-status flip — so in live play, Rourke hitting 0 HP was silently treated exactly like any other survivable downing: she "restocked" and the mission carried on. This is the exact sim-log line the Taunt addendum earlier in the main log already quoted without flagging it as wrong ("exempt from permadeath — always a standard restock," Mission 8's own Choir-focus-fire test) — the bug was hiding in plain sight in that log's own earlier verification text. Confirmed against the Independent Campaign doc's own §6a, which has never said this: "Rourke going to 0 HP doesn't get redirected onto someone else and it doesn't get waved off — it ends the mission attempt outright and sends the player back to the briefing screen to try again, with nothing about that attempt ever resolving, including the permadeath check itself." The live engine and the design doc had genuinely diverged, not just a stale-comment situation.

**The fix, modeled directly on the mission real-time clock's own evaluate/apply split (the closest existing precedent — both are "void this attempt, cost nothing" mechanics).** `MissionOutcome` (`engine/mission.ts`) gains a third value, `"commander_down"`, distinct from both `"win"` and `"loss"`. `Mission.handleDowned()` now checks `PilotRecord.exemptFromPermadeath` itself, first thing, before the rescue-failure check, before `wasDowned` tracking, and — the doc's own explicit requirement — before `evaluatePermadeathCheck` is ever called: if the downed unit is the exempt pilot, `this.outcome` is set to `"commander_down"`, the new `Mission.commanderDownPilotId` field records who (data-driven, not a hardcoded id, so this stays correct if the flag ever moves to a different pilot), a log line is pushed, and the method returns immediately — nothing else in `handleDowned` runs for that downing. `evaluatePermadeathCheck`'s own exempt branch is left in place, not deleted (a test or any future caller evaluating a downing in isolation, outside a live Mission, still gets a technically-correct answer from it), but its comment now says plainly that live play never reaches it for this pilot any more.

`engine/campaignState.ts` gained `applyCommanderDownAttempt(state)` — unconditionally clears `activeMissionAttempt`, the one piece of real `CampaignState` mutation a voided attempt needs, same "costs nothing mechanical" shape `applyMissionTimeout` already established for a 12-hour recall. No evaluate/apply split needed here (unlike the timeout functions) — by the time anything calls this, `mission.outcome` already IS `"commander_down"`, so there's nothing left to check.

`scenes/Battle.ts` gets a new `drawCommanderDownOverlay()`, branched off `mission.outcome === "commander_down"` ahead of the existing win/loss overlay code — a distinct "COMMAND DOWN" screen (red title, same visual language as `Boot.ts`'s own RECALLED notice, deliberately: both exist to tell the player an attempt was voided through no fault of the roster, not that they lost), naming whichever pilot triggered it, stating plainly that nothing was lost, and a single "return to briefing" button that goes straight to `MapSelect` — **not** to `Debrief`. This is the mechanical heart of "restart from mission briefing": `MapSelect` is this codebase's own mission-briefing screen (`mission.briefing` text is what renders on every mission card there), so skipping Debrief entirely and landing on `MapSelect` means no earnings, no permanent-loss application, no Munti-guarantee check — none of Debrief's mission-resolution machinery ever runs for a voided attempt, matching the doc's "nothing about that attempt ever resolving" line exactly. `activeMissionAttempt` is cleared via `applyCommanderDownAttempt` the first time this overlay draws, guarded by a new `commanderDownAttemptCleared` flag so a still-open overlay doesn't re-save `CampaignState` on every redraw while the player is looking at it.
