## Addendum, 30 Aug 2026: Tier 1 (complete) — door-clustering and the player spawning on top of an NPC

Consolidated Build Plan (29 Aug 2026), Tier 1, items #1 and #2 — the last two of the tier's four Hub collision/movement bugs (see the earlier same-day addendum, `Bloom_Wars_Build_Log_Addendum_Tier1MusterCrossDeckAndMeks_30Aug2026.md`, for #3 and #4). Maxime: "fait tout en batch. 1 a la fois. jusqua ske tu manque de credit" — oui, go.

**Root cause, both bugs, one shared shape.** Every door in `DOORS` has exactly one fixed `(x, y)` trigger point on its near side and one fixed `(toX, toY)` landing point on its far side. The far side already got fixed once, 26 Aug — two NPCs landing on the identical pixel would permanently deadlock each other via `tryMoveNpc`'s own collision check, fixed by jittering the landing with rejection sampling (`pickDoorLanding`, still in place, untouched by this pass). Two more uses of a door's literal fixed point never got the same treatment, because neither predates the multi-deck Grid the way the muster bug did — they're just gaps in the original 26 Aug fix's own scope:

1. **Door-clustering (#1).** Every "walk to this door to hop through it" call site — four of them: `completeDoorHop`'s own multi-hop continuation, `updateNpcRoaming`'s journey-resume and explore branches, and `sendToMuster`'s cross-deck branch (new this session, see the muster addendum) — set `targetX/targetY` straight to the door's literal `(x, y)`, no jitter. Several NPCs converging on the same door (muster, explore, a resumed journey) all beeline for the identical point; `tryMoveNpc`'s per-step collision then packs them into a ring tight around it. `DOOR_RADIUS`'s own 45px arrival tolerance means this was never a true deadlock the way the landing-side bug was — a blocked NPC still eventually gets close enough to register "arrived" — but a doorway a few NPCs deep in that ring reads as jammed to the player, both visually and for `isAtDoor()`'s own collision-bound approach, since the player is blocked by NPCs the exact same way NPCs block each other (`handleMovement`'s own `PLAYER_R + NPC_R` check, unchanged by this pass).
2. **Player spawns on an NPC (#2).** `switchRoom` — the player's own door-crossing — placed the player at the door's literal `(toX, toY)` unconditionally, with zero collision check. This is the identical single-fixed-point bug the 26 Aug fix solved for NPC-on-NPC landings; the player's own landing was simply never brought in line with that fix, since `switchRoom` predates it and nothing had revisited this exact spot since. An NPC can perfectly well be standing at or near a door's landing point when the player walks through — same door, same coordinate — so the player needs the same treatment NPCs already get, not a separate system.

**The fix, one function reused three ways.** Generalized `pickDoorLanding` into `pickPointNearDoor(center, occupants, selfRadius)` — same jitter-and-reject logic, now parameterized on which point it's jittering around and which body's radius the rejection check should use (an NPC's `NPC_R`, or the player's `PLAYER_R` — matters because the real collision math elsewhere in this file is always `radiusA + radiusB`, never a hardcoded constant, and the old function had baked in `NPC_R + NPC_R` for both sides). `pickDoorLanding` itself is now a one-line wrapper over it, unchanged in behavior. New `pickDoorApproach` is the same wrapper for the near side. New private `approachDoorTarget(npc, door)` is the single place all four NPC call sites get their walk target from (pick, then `clampToDeckFloor` the result — same reason `completeDoorHop` already clamps its own landing point: a raw jittered point can land fractionally outside the deck's real floor, and an unreachable target would silently reproduce the exact "never satisfies the arrival check, retries forever" failure the file's own `arriveThreshold` comment already diagnosed once, for a different cause — clamping the target itself, not just each step toward it, is what keeps that from happening here too). `switchRoom` calls `pickPointNearDoor` directly with `PLAYER_R` and clamps the same way.

Traced by hand rather than assumed safe: worst case, a jitter can land a target up to `DOOR_LANDING_JITTER_DIST` (30px) past the room's real boundary, which — pre-clamp — would have made the target permanently unreachable (an NPC can only ever get `NPC_R`/`PLAYER_R` pixels inside a boundary edge, per `tryMoveNpc`'s own clamp) and put the file right back into the exact deadlock-by-unreachable-target shape it already fixed once. Clamping the target itself, not just each step toward it, closes that off — the same reason `completeDoorHop`'s landing side already does it.
