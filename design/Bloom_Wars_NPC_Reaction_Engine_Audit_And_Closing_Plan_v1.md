# THE BLOOM WARS — NPC Reaction Engine: what's actually live, and a closing plan for the *current* (not v6) recipe

**Status: paper only, zero code touched, per Maxime's own instruction this pass — "only plan for now."** Maxime's framing: the v6 formula (`Reaction_Formula_Applied_Model_v6.docx`) is his own current, tested version, but the game keeps running the older recipe (`design/Bloom_Wars_NPC_Reaction_Engine_v1.md`, 25 Aug) until after EA. Before touching anything, he wants to know: does *that* older recipe actually work as designed, in the live game, today? Where code is missing, this doc finds a way to make it work — but as a plan, not a build. Checked directly against the live TypeScript source (`src/data/*`, `src/engine/*`), not assumed from the design docs alone.

## 1. What's actually real in the live game, piece by piece

| Formula piece | Live status | Where |
|---|---|---|
| **Gate 0** (does this pilot even react) | **Real, but narrow.** Implemented exactly as designed — a tunable base chance nudged by drunk/panic/worry. But its own file header says outright it's wired to **exactly one call site**: Hub's `speak()` (the Talk verb). Every other reaction trigger — ambient idle ticks, hot topics, muster relay, gossip, Grief Catalyst — fires whenever its own eligibility condition is met, with no Gate 0 check at all. | `src/data/reactionGate.ts` |
| **c — the catalyst/animal pick** | **Real**, all nine animals, real content banks. | `src/data/ambientLines.ts`, `catalystProfile.ts` |
| **b⁴ — the echo pick** (Love/Fear/Anger/Sadness) | **Real, deterministic priority ladder** — drunk → panicking (Stress) → worried → low morale → else random across all four. Works exactly as coded. | `pickSoloEcho`, `ambientLines.ts` |
| **A — the 12-position Planet/pillar diagram** | **Not built at all.** Checked `AmbientPilotState` directly — catalyst, stage, stress, morale, drunk, worried. No Planet field, no pillar field, anywhere. This is the whole reason Background Zones has nowhere to plug in yet — it's not an assignment-method question, there's no seam to assign into. | *(nowhere)* |
| **Self vs. environment** | **Not built**, and the design doc already says so honestly. Confirmed independently — nothing reviewed gates action availability on who's watching. | *(nowhere)* |
| **Self vs. other (the loop)** | **Real, but simplified.** Grief Catalyst is genuinely live (ported 28 Aug, fires from `Debrief.ts` on a true permadeath), not sandbox-only. | **Tiebreaker = character history, not random** | **True in the sandbox and on paper. Not true in the live game.** `pickSoloEcho`'s own idle/fallback case is a flat `Math.random()` across all four echoes — no Favorability, no bond history, nothing. `ambientLines.ts`'s own file header already says why: the sandbox's history-biased version depends on a persistent Favorability store that "doesn't exist on the real PilotRecord/CampaignState yet." This is the single most-repeated principle across every version of this formula, and it's currently the game's biggest gap between what's claimed and what's shipped. | `ambientLines.ts` header, confirmed |

## 2. One piece of real drift, worth flagging on its own

`catalystProfile.ts` (26 Aug) gives every pilot **sub-animals** — a distinct catalyst for instinct/thought/action, one day after the design doc's own "reopened question" explicitly says the three-animal path is *"not adopted here, just surfaced."* Checked what it actually feeds: only the chat-keyword dictionary match (`CATALYST_DICTIONARY`), not `pickSoloEcho` at all. So it's not really the three-animal path the design doc was weighing — it never touches the echo pick — but the design doc doesn't say that, and a future reader could easily conflate the two. Recommend a one-line doc fix, not a code change: note in `Bloom_Wars_NPC_Reaction_Engine_v1.md` that sub-animals shipped for chat-flavor purposes only and don't answer the three-animal reaction question one way or the other.

## 3. The closing plan — small, additive, scoped to the *current* recipe only

Nothing here touches v6. Ordered cheapest/highest-leverage first, same discipline every other pass in this project uses:

1. **Build the real, persistent Favorability store.** This is the one fix that closes the biggest gap (§1's last row) and is already fully spec'd by the sandbox — it's a port, not a new design. Once it exists, `pickSoloEcho`'s idle branch can lean its random pick the way the sandbox already proved out (close bond → love/warmth, toxic bond → anger/fear), which is what actually makes "the formula never supplies the tiebreaker, history does" true in the shipped game instead of just in the design docs.
2. **Give the Planet/A axis its first real code seam.** Not the full 12-position system — just one persisted field per pilot, piggybacked onto the same CampaignState work item 1 already needs (both are "give a pilot durable per-pilot state beyond Stress/Morale"). This is exactly the hook Background Zones' Zone×Pressure seed needs to write into once it's real.
3. **Widen Gate 0 past its one call site**, deliberately not to every verb (deterministic verbs stay reliable on purpose, per the file's own existing carve-out) — the natural next candidates are ambient idle ticks and hot-topic pop-ins, the two places the design doc's own "most pilots, most of the time, don't react" framing was clearly aimed at.
4. **Confirm Command Vacuum/`recordMuntiLost()` directly** before the propagate row above gets treated as settled — cheap, and this pass didn't re-verify it.
5. **One documentation fix, not a code item:** note the sub-animal/three-animal distinction from §2 in the design doc itself, so it stops reading as an open question the code quietly half-answered.

## 4. What this doesn't change

Same standing rule as every other paper pass in this project: nothing here gets built before Maxime says so, and per this conversation specifically, nothing here jumps ahead to v6 — this plan is entirely about making the *current, shipped* recipe match its own stated intent, which Maxime asked for directly and separately from the v6 upgrade question.
