## Tier 5 — abil_ambush stealth cloak redesign: SHIPPED, verified

Maxime's own spec: "stealth cloak 3 turn, can move whilestealth. can attack while stealth. does 2x dmg after exiting stealth. its to give sweep a pvp use too and make ambush something usefull in game." Ambush was a one-shot reactive trick built on Overwatch's own trigger (concealed + overwatch together, one held shot, gone the instant it fired). Now: activating sets a new `stealthTurnsRemaining` field (3 rounds) alongside `concealed`; the per-round reset loop decrements it instead of blanket-clearing concealment while it's active, so the unit's own later turns are fully normal (move, attack) while hidden. `resolveAttack()` doubles the damage of the specific attack that breaks an active cloak (gated on the new field, not on `concealed` generally, so `abil_screen` is untouched) and tags it "DECLOAK STRIKE" in the log. Separately, `engine/ai.ts`'s `isVisibleTo` had `concealed` checked *before* `revealedUntilTurn` (abil_sensor_sweep's paint) — meaning a swept ambusher stayed invisible regardless — reordered so a sweep now beats concealment the same way it already beat burrow. That reorder is the literal "give sweep a pvp use" half of the request; `abil_sensor_sweep` itself is still player-only (no hostile-side/PvP use exists yet to actually run in), so this is the seam opened, not a finished PvP mode.

Four existing tests that encoded the old reactive-shot behavior were rewritten (they failed exactly as expected the moment the mechanic changed); one new test proves a swept unit is visible through concealment. `npm run sim:batch` run for regression-checking per Tier 0's own precedent — 289/400 (72%), matching baseline, though confirmed the bot's own AI doesn't call `ambush()` at all yet (`playerAi/types.ts`'s own note), so this run confirms non-interference rather than exercising the new mechanic live.

## Engine fix: extract_unit role fallback (both campaigns)

Maxime, after Mission 19: *"you shouldnt make a single nsmed chsracter the most important part of a mission. use a role. un case the player doesnt bring those npc with him or they die. dont forget other than the mc. no one is safe from perma death."* Then: *"if you did something similar in another mission. better fix it too."*

Full writeup: `design/Bloom_Wars_Build_Log_Addendum_ExtractUnitRoleFallback_31Aug2026.md`

- **A real bug, not just design taste.** Single-named-pilot `extract_unit` missions (`objectiveParams.extractUnitId`) resolved the target with a raw `unitById(id)` lookup. If that pilot was never deployed — left home in a squad-selection pass, or permanently lost to an earlier mission's own permadeath — the lookup returned nothing, `extractedUnitId` could never be set, and the mission's only path to a win was permanently closed. Every run would time out via the turnLimit loss branch with no error and no indication why.
- **Searched the whole objective system first** to confirm scope: `extractUnitId` is the only field anywhere in `objectiveParams` or `MissionEvent` triggers that hardcodes a specific pilot as mechanically load-bearing (`rescue_pilot`'s `canRescue` already takes any deployed rescuer; no mission uses a `unit_downed` trigger keyed to a named pilot for anything objective-relevant). One engine fix covers every affected mission at once, zero mission-data edits: House Amaranth Missions 3/5/7/11/14/17 (`pilot_orin`), Warden's own `pilot_anand`/`pilot_iyari`/`pilot_lask`/`pilot_solheim`/`pilot_okafor`, and Team One's `pilot_trav`.
- **The fix:** `tagExtractionTarget()` now falls back to the first living player unit in deploy order when the named pilot isn't on the board — deterministic, not random. If the named pilot IS deployed, nothing changes (still the target, still a real loss if they go down mid-mission — Maxime's own "no one is safe from permadeath" stakes preserved). Added `resolvedExtractUnitId`/`resolvedExtractionTargetId` as the one place this resolves; every downstream reader (engine win/loss checks, Player AI's extraction-seeking heuristics, Battle.ts's HUD line and on-board green ring) now goes through it instead of re-deriving from the literal configured id — the HUD line had its own real bug baked in too, showing "extracted — clear" from turn 1 when the named pilot was never deployed at all.
- **Verified, not just typechecked.** A scratch harness (deleted after use) built Mission 17's own squad minus Orin and ran it through the real Player AI loop: mission's own 12-turn limit → 0/30 win but a legible, real loss (not a hang); turn limit forced to 40 to isolate "is extraction possible at all" from "is 12 turns enough for a smaller squad" → 20/30 (67%), genuinely winnable. Full squad including Orin re-sim'd unchanged at 75% (113/150), matching Mission 17's already-documented number exactly — the common case is provably untouched.
- **Added `src/engine/__tests__/extractUnitFallback.test.ts`** — 6 permanent regression tests (named pilot present: unchanged; named pilot absent: falls back, wins, still a real loss if the fallback target itself goes down) so this can't silently regress.
- **Verification:** typecheck/lint clean, 1192/1192 tests (6 new), zero regressions.
