**7. \"brief\" and \"debrief\" do the same thing, and \"aoc, ...\" doesn't reach the CO by name — 2 Sep 2026. Unlike items 1-6, this one was actually diagnosed against the live repo (staged into a cloud sandbox, per this project's own standing rule — nothing here is guessed from memory), because Maxime asked for a plan this time, not just capture. BUILT and committed the same day — see item 7a below. Original hold, kept for the record: \"dont fix yet. just tally and plan.\"**

Maxime's own report, verbatim: \"brief does the same thing as debrief. it should not. brief is before a mission debrief is after a mission. arrangemnt of content should regonise itself if the player say aoc, debrief. or aoc, brief.\"

*Diagnosis, part A — brief and debrief are the same bucket.* `src/data/chatIntent.ts`'s `DEBRIEF_KEYWORDS = [\"brief\", \"debrief\"]` (added earlier the same day, 2 Sep — see `Bloom_Wars_Build_Log_Addendum_ChatBriefDebrief_AmbientMinigameRoomGate_02Sep2026.md`) feeds one `detectDebriefRequest()` that returns a plain yes/no — it never distinguishes which word was actually typed. `Hub.ts`'s `submitChat` (~line 2586) checks that single boolean and always calls `handleDebriefRequest()` (~line 3336), which only ever returns the POST-mission recap — `campaignState.lastMissionEcho`'s win/loss content rendered through `renderHotTopicLine`. There's no PRE-mission content anywhere in the current build; \"brief\" was folded into the same bucket as \"debrief\" on the (reasonable but incomplete) read that both meant \"tell me about the mission,\" without splitting before-the-mission from after. Confirmed directly against the live file.

*Diagnosis, part B — \"aoc, ...\" doesn't reach him.* The CO-only gates in `submitChat` (build/debrief/confide/remove-pilot, all 1-2 Sep) check physical proximity only — `nearby?.pilotId !== CO_PILOT_ID`, where `nearby` is whichever NPC is literally nearest within `APPROACH_RADIUS`. None of the four look at what the player typed. That's different from the six newer social-action verbs (praise/insult/etc., same 2 Sep pass), which go through `resolveChatTarget()` — that one tries `extractNamedTarget()` (matches literal words of an NPC's `displayName`) FIRST, nearest-in-range only as the fallback, so \"well done, Corin\" reaches Corin specifically even if someone else is standing closer. The CO's four requests never got that same treatment. And even if they had, it still wouldn't catch this: `extractNamedTarget` only matches literal words split out of the CO's real `displayName`, `\"Arangement of Content\"` (\"Arangement\"/\"Content\" survive its filter, \"of\" is dropped for being under 3 characters) — \"aoc\" isn't a substring of that name anywhere, so it needs its own alias list, not just the existing machinery pointed at him.

*Plan — not built, for Maxime's go-ahead:*

1. Split the keyword buckets in `chatIntent.ts`: `DEBRIEF_KEYWORDS = [\"debrief\"]` stays wired to the existing `handleDebriefRequest()` (post-mission recap, unchanged behavior). New `BRIEF_KEYWORDS = [\"brief\"]` / `detectBriefRequest()` / `handleBriefRequest()` in `Hub.ts`, under the identical CO-only gate/redirect shape the other four already use (\"Ask the CO about that — find him in the grotto.\" if he's not the one nearby).

2. Open question worth a real answer before writing `handleBriefRequest()`, not guessed at here since it's a content/scope call: what should \"brief\" actually say? Debrief reused existing content wholesale (the mission-echo win/loss lines) — there's no equivalent pre-mission content sitting around to reuse the same way. Three options, smallest first:
   - (a) Minimal, no new content: an honest placeholder in the same voice as debrief's own \"Nothing to report yet — you haven't flown a mission\" line — something like acknowledging there's no formal briefing content yet and pointing at the mission board. Zero new systems touched.
   - (b) Small and real: pull the name of whatever mission is actually next/available (the same list `MapSelect.ts` renders) and have the CO name-drop it in one generic line. A small but genuinely new wire — Hub.ts reading mission-registry data for the first time in this feature.
   - (c) Bigger: a real pre-mission objective briefing (what the mission actually asks you to do). Meaningfully more scope, new authored content — probably its own later pass, not this one.
   Leaning (a) for parity with how debrief itself got scoped (\"for now,\" reuse over new writing), but this is Maxime's call, not something to decide blind.

3. Add a small `CO_ALIASES` list (\"aoc\" at minimum — need Maxime's call on whether \"commander\"/\"co\" should also count, since a bare two-letter \"co\" risks false-matching ordinary sentences far more than \"aoc\" does), checked the same word-boundary way `extractNamedTarget` already checks display-name words. When a message names the CO this way, the CO-gated checks in `submitChat` (build/debrief/brief/confide/remove-pilot) should resolve to him the way `resolveChatTarget` already lets a named target beat \"nearest\" for the six social verbs — same scope as that existing precedent (same deck, not literally nearest-only) rather than a brand-new \"radio the CO from anywhere on the ship\" behavior, unless Maxime specifically wants the bigger version.

4. New/updated tests in `chatIntent.test.ts` (plus Hub-side coverage) pinning: \"brief\" alone no longer triggers the post-mission recap; \"debrief\" is unaffected; \"aoc, debrief\"/\"aoc, brief\" reach the CO even when he isn't literally the nearest NPC.

5. Full verify (tsc/eslint/lint-spoiler/vitest/build) plus a live Playwright pass through the real chat UI, same standing bar this project already holds chat-intent changes to, before anything gets committed back to the device repo.
