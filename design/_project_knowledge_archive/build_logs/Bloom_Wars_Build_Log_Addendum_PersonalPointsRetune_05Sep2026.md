# Build Log Addendum — Personal Points Earn-Rate Retune, 5 September 2026

Right after the Shop UI collision fix, in the same live-testing pass — Maxime, having just watched real personal-point balances against real branch/tier costs on his own machine: **"point take a while to get, we should increase the average."**

The actual target was put to him directly (AskUserQuestion) rather than picked for him, since "increase the average" alone doesn't say by how much or toward what goal — personal points are spent on a real, addable total (weapon branches 150+220+300+400=1070, the G→A tier ladder 60+90+140+210+320+500=1320, Mek secondary 180 — 2570 to fully max one pilot), but nothing on the earning side had ever been sized against that number, so there was a genuine range of reasonable answers rather than one obvious fix. His answer: **a favorite/main pilot should be able to fully max out — tier A, all 4 weapon branches, Mek secondary — well inside one campaign.**

## What shipped

`engine/campaignEconomy.ts` — `KILL_BONUS`, `SURVIVAL_BONUS`, and `OBJECTIVE_BONUS` (per-kill, per-mission-survived, per-mission-won personal-point awards, feeding `computeMissionEarnings()`) all tripled: 5→15, 5→15, 10→30. A straight, uniform 3x scale-up, not a reshuffling of the ratio between them — a kill is still worth exactly 1 kill-bonus, an assist is still priced as a fraction of that same value (`Math.round(KILL_BONUS * assistCredit)`, untouched), survival and objective are still flat per-mission terms at the same relative weight to each other and to kills as before. Chose a uniform scale specifically so nothing about *how* points are earned changes, only *how much* — see "what this doesn't touch" below for why that mattered.

**The arithmetic behind "roughly mission 25-30 of 36":** a central, frequently-deployed pilot averaging a couple kills a mission, usually surviving, mostly on winning missions, earns in the neighborhood of 75-120 personal points per mission at the new rate (15/kill × ~2-3 kills, +15 survival, +30 objective). Against a 2570-point full max-out, that's roughly 25-30 missions of typical play for that one pilot — inside Warden Company's 36-mission length with genuine room to spare, not a photo finish. A support-role pilot (Munti, mostly assist fractions rather than finishing blows) earns slower and won't fully max by the same point — that's the intended shape per Maxime's own framing ("your main"), not an oversight: everyone gets meaningfully geared over a campaign, the squad's actual focus pilot is the one expected to hit the ceiling.

## The neighbor this touches, checked rather than assumed

`data/heirlooms.ts`'s `ARISTOCRAT_SIGNING_POOL` (= 650, a late-recruited Heirloom pilot's starting personal-point stipend) had its own supporting comment built directly on the OLD earn rate — "mission earnings run KILL_BONUS(5)/SURVIVAL_BONUS(5)/OBJECTIVE_BONUS(10)... roughly 25-40 points on a good mission... a lifetime ceiling of maybe 600-950 personal points EARNED... could join with six missions left and never afford a single rank on anything." Read that comment fully before touching anything, per this project's own standing rule about checking what's sitting next to a fix.

**The constant's actual VALUE turned out not to need changing** — re-reading its own reasoning, 650 was never derived from the earn rate; it's `HEIRLOOM_ABILITY_RANK_COST` ranks 2+3 on one ability (250+400), a "the house paid for the weapon to be worth carrying" number that's deliberately independent of how fast anyone earns points. What DID need fixing was the comment's own supporting arithmetic, which was now stale and would mislead a future read: updated "25-40" → "75-120" and "600-950" → "1800-2850" (both straight 3x, matching the actual retune), and added a line noting the original "six missions left and never afford a single rank" framing is less true now (six missions at the new rate nets maybe 450-720 from ordinary play alone) — but the pool's own justification never depended on that scarcity being severe, only on the signing bonus being a fixed, legible amount, so nothing about its actual value changes.

**Also checked and confirmed clean:** `Bloom_Wars_Design_Principle_OptionalCombat_Rewarded_29Aug2026.md` — the locked design pillar that survival+objective points must stay a genuinely viable non-combat baseline relative to what real engagement pays, plus Maxime's own explicitly-deferred follow-up ("should killing Bloom be made *relatively* more lucrative — no idea, need late-game playtest first"). A uniform 3x scale preserves both untouched: the ratio between kills/survival/objective is exactly what it was, so the non-combat baseline is exactly as viable relative to combat as it was before, and the deferred "make killing relatively more lucrative" question is still just as open and still un-decided — this retune answered "how fast, overall," not "combat vs. non-combat, relatively," which were always two separate questions and stay that way. `build_log/engine_systems/house_rules.md` was also checked — no personal-point figures live there, nothing to update.

## Tests and verification

No test hardcodes a literal expected point total against these three constants — every existing assertion in `campaignEconomy.test.ts` references `KILL_BONUS`/`SURVIVAL_BONUS`/`OBJECTIVE_BONUS` by name (e.g. `expect(earnings["pilot_barasj"]).toBe(SURVIVAL_BONUS + OBJECTIVE_BONUS)`), so they scale automatically with the constants and needed no edits. `tsc --noEmit`, `eslint .`, `lint-cast-collision.mjs`, `vitest run`, `vite build` — all clean, **same 94 files / 2221 tests** as the Shop UI fix earlier tonight (a pure numeric retune, no new test file). Committed to the device — `engine/campaignEconomy.ts` and `data/heirlooms.ts` — with a fresh mtime check on both immediately before committing, zero drift, zero conflicts.

## Still open

- Not sim-validated against `combat_sim.py` — these are personal-economy pacing numbers, not combat balance numbers, so that script was never the right tool for this one; same category of "argued, not simulated" placeholder every other unset economy figure in this project already carries, except this one now has a stated, reasoned target (mission 25-30 full max-out) rather than no target at all.
- Nobody has watched a real pilot actually hit this pace across real missions yet — the 75-120/mission estimate assumes "a couple kills," which is itself an assumption about how combat-focused a typical mission is for a typical pilot, not a measured average. Worth Maxime's own read after a real play stretch.
- The company-pool side of the economy (mission `rewardPoints`, `computeMissionCompletionBonus`, Beacon crate/charge prices, bay-build costs) was untouched — this pass was personal points only, per what was actually asked.
