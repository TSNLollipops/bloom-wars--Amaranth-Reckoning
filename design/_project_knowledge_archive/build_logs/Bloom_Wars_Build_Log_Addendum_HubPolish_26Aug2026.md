## 29. Hub polish, fourth pass — hardening the door-landing collision risk, 26 Aug 2026

Same session, same hour-long unattended stretch as §28 (Maxime still working the tactical side separately). Picked the next item explicitly still flagged open across §26/§27/§28's own closing notes: the jittered door-landing collision risk from §24 Bug B, described there as "a real, honest residual risk, not swept away." Stayed off anything combat/mission/tactical-adjacent again, same discipline as §28 — this pass touches only `Hub.ts`.

**Measured the actual risk before touching anything, rather than trusting the old comment's own claim.** §24's fix (landing at a `pointNear()`-jittered point instead of the door's exact coordinate) called the residual risk "astronomically less likely" than the guaranteed exact-pixel stack it replaced. That was never actually measured. A quick Monte Carlo check (a temporary, unshipped `tsx` script, 200,000 trials, importing the real `pointNear` from `data/npcBonds.ts`) put a single jittered draw at **~35.7% odds of landing within collision distance (NPC_R+NPC_R = 32px)** of a second NPC who drew the same jitter — because `pointNear` places a point at an *exact* distance from center on a random bearing, so two draws are two points on the same circle, and the only thing separating them is the angular gap between two random angles. Nowhere near astronomical — a real, hittable rate in ordinary play. Worth naming plainly: the old comment was optimism, not a measurement, and it's corrected in place in the code now (not deleted — same "correct stale comments, keep the history" convention this file already holds itself to) rather than left standing.

**The fix: rejection sampling against whoever's actually in the room, not a wider or different-shaped jitter.** Considered widening `DOOR_LANDING_JITTER_DIST` or switching to a variable-radius disc first — measured that too (radius drawn uniformly 20–50 instead of a fixed 30) and it only brought the rate down to ~29.5%, a marginal win for a change that also alters how far from the door an NPC visually lands. Rejection sampling is a bigger win for a smaller, more targeted change: new `pickDoorLanding(door, occupants)` keeps drawing a fresh `pointNear()` jitter (unchanged distance, unchanged shape) until it clears collision distance of every NPC already in the destination room, up to `DOOR_LANDING_MAX_ATTEMPTS` (5) tries — independent ~35.7%-per-try odds means 5 misses in a row is under 0.1%. `completeDoorHop` now calls this instead of a single `pointNear()` draw, passing `this.npcs.filter(n => n !== npc && n.room === door.toRoom)` as the occupants to avoid. The one subtlety worth stating plainly: a genuine same-frame double-arrival (two NPCs completing a door hop on the identical `update()` tick) still resolves correctly without any extra synchronization — `this.npcs` is updated synchronously as each NPC lands (`setNpcRoom` writes room/x/y immediately), so whichever one's `completeDoorHop` happens to run second in that frame's loop already sees the first one's real, just-placed position when it builds its own occupants list.

**Verified with the real method, not just the isolated math.** Forced the exact same-frame double-arrival scenario 500 times through the actual `completeDoorHop()` — both NPCs reset to Rec Room with `travelTargetRoom` set to the same destination, `completeDoorHop(a)` then `completeDoorHop(b)` called back to back exactly as the frame loop would — and measured the resulting distance each time. Result: **1/500 landed within collision distance (0.2%)**, down from the old single-draw rate of ~35.7% — consistent with the predicted sub-0.1%-at-5-tries figure given normal sample variance at n=500. Zero console errors.

`npm run typecheck`/`lint`/`build` all clean. `npm run test`: 732/734 this run (2 failures, both exclusively in `commanderDown.test.ts`) — the same pre-existing flake tracked since §8, confirmed unrelated since this pass touched only `Hub.ts`.

Files synced to the device: `src/scenes/Hub.ts` (the only file this pass touched). `main.ts`'s temp `?scene=`/`window.__bwGame` hook was added and reverted, grep-confirmed absent before syncing, same convention as every prior pass. Checked the device's actual current mtime before this commit rather than assuming the last-known value still held — the lesson §28 itself just recorded.

**Real, honest gaps left for later, not silently closed:** rejection sampling reduces the collision rate to a small residual, it doesn't make it mathematically zero — a genuinely unlucky run (5 misses in a row, ~0.06% per attempt-pair) can still stack two NPCs, at which point the existing stuckMs/sidestep-on-give-up mechanism (§24 Bug C) is still the real backstop, unchanged by this pass. `DOOR_LANDING_MAX_ATTEMPTS`/`DOOR_LANDING_JITTER_DIST` are both still placeholder numbers. `VerbDef.room` generalization (§25) and the `socialLog`/relationship-status UI gaps §27/§28 already closed the current-status and history halves of — everything else on those two lists is unchanged.

## 31. Hub polish, sixth pass — worried NPCs also speak up more, 26 Aug 2026

Same day, straight off §30. §30's own closing note flagged one deliberate scope call: worry only changed line *content* (the fear pool), not whether an NPC reacts at all — Gate 0's engagement chance stayed untouched, since that felt like a separate judgment call worth surfacing rather than assuming. **The call, and why it's not just "reuse the panic penalty."** Gate 0 (`reactionGate.ts`) already nudges reaction chance off a pilot's state — drunk pilots are looser (+0.15), a pilot at the Stress panic threshold is too consumed by their own moment to register ordinary chatter (−0.30). Worry reads as the opposite of panic even though both are nominally "fear": panic is overwhelmed/shut-down, worry about a crewmate is the anxious, wants-to-vent, wants-to-check-in kind — so it's a bonus, same direction as drunk, not a second penalty. New `GATE0_WORRY_BONUS = 0.1`, smaller than drunk's own +0.15 since worry is a quieter background state, not full looseness. The two fear-flavored deltas (panic's −0.3, worry's +0.1) can both apply to the same pilot at once — a worried pilot who's also independently panicking from Stress nets negative, panic's own penalty dominates, which is correct: crossing the Stress panic threshold is a much more acute state than background mission-worry, and nothing about worry should override that.
