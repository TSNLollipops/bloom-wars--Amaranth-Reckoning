Closes the gap `Bloom_Wars_Build_Log_Addendum_MaserLanceShipped_05Sep2026.md` flagged the moment Maser Lance itself shipped, and `Bloom_Wars_Now_And_Next.md`'s "Needs Maxime's call" #5 asked about directly: a Tank pilot with Maser Lance equipped, if AI-piloted in the Rec Room or a `npm run sim` batch, simply never fired it — not broken, just unused in that one context, the same gap Missiles had before its own AI pass existed. ## What shipped

`chooseMaserLanceDirection` (`src/sim/playerAi/abilities.ts`), wired into the same decision chain as `chooseMissileTile` (`src/sim/playerAi/index.ts`, right after the missile branch) and dispatched by `src/sim/driveMission.ts`'s new `"maser_lance"` case straight to `Mission.maserLanceStrike`. A Tank pilot with the branch equipped, AI-piloted at MODERATE or HARD, now fires it on the same "obvious trigger, gated by the profile, safe to under-use" contract every other ability heuristic in this file already follows.

**The one real difference from `chooseMissileTile`, and why it isn't a copy-paste job.** Missile/Fire Support both score a radius around a tile the function picks itself, scanning a bounding box. A cone can't be summarized that way — the widening-wedge formula (1/3/5 tiles wide at forward-steps 1/2/3, laid out along the chosen direction's own perpendicular) lives in `engine/mission.ts`'s `maserLanceConeTiles`, private on purpose. Rather than duplicate that geometry a second time in the AI layer — exactly the kind of drift `Cross_Project_Writer_Note.md`'s "verify against the actual current file" habit exists to catch — `chooseMaserLanceDirection` asks the engine for it: it walks `Mission.getMaserLanceDirectionTargets`' own candidate tile list (every in-bounds tile along each of the 8 legal directions), resolves each candidate's real footprint via `Mission.previewMaserLanceCone`, and de-duplicates by the resolved cone itself — every tile along one ray previews the identical cone, so each of the 8 real directions gets scored exactly once, not once per candidate tile. `PlayerAiMissionContext` (types.ts) picked up two new optional methods or a live `Mission` instance no longer satisfies it structurally.

Scoring itself (`coneScoreOver`, new, local to abilities.ts) is `strikeScoreAt`'s exact rule — hostile count, +2 for an emergent-tier boss, +0.5 when the hit threatens a living VIP, hard-reject any direction whose cone would also catch a friendly — just evaluated over an already-resolved tile set instead of a tile-plus-radius. Not folded into `strikeScoreAt` itself: bending that function's signature to also accept a raw tile list would make every existing radius call site (Fire Support, Missile) read as though it had to think about a shape it never actually has.

Profile-gated the same way Missile/Fire Support are: `abil_maser_lance` added to `PlayerAiAbility`/`ALL_ABILITIES` (profile.ts). MODERATE and HARD get it (they spread `ALL_ABILITIES`); EASY and LEGACY don't, matching those tiers' existing omission of Missile/Fire Support — a first-time player wasn't using a granted ranged ability before this pass either, and this doesn't change that.

## Verification

No `device_bash` on this device — this device_bash-less session did the now-standard thing: staged the full `src/data`, `src/engine`, `src/sim` trees (everything the sim harness's own dependency graph touches; `src/scenes/**` never enters it, confirmed by grep before assuming it) plus `package.json`/`package-lock.json`/`tsconfig.json`/`eslint.config.js`/`vite.config.ts`/`tools/lint-cast-collision.mjs` into a cloud sandbox, ran `npm install`, then a scoped `tsc --noEmit` (a temporary `tsconfig.verify.json` narrowing `include` to those three trees — `scenes/`'s own huge Phaser files have nothing to do with this change and were never staged) and `npx vitest run` against the sim + the two granted-ability engine test files.

Baseline (before this change): clean typecheck, 77/77 tests passing across those files — confirming the staged subset was complete before touching anything. After the change: clean typecheck, clean `npx eslint` on every changed file, clean `node tools/lint-cast-collision.mjs` (33 reserved names, 11 approved crossover names, nothing new collides), **82/82 tests passing** (77 pre-existing + 5 new, zero regressions). `git clone`ing the real repo and driving a real terminal on the device were both tried first and both correctly refused by this session's own safety rails (an external clone; a terminal only grantable in click-only mode) — reconstructing the dependency tree from the connected folder was the honest way to get a real toolchain run instead of skipping verification.

**New test file: `src/sim/playerAi/__tests__/abilities.test.ts`** — the first direct unit-level coverage this module's own ability-trigger functions have had (Missile/Fire Support are only exercised indirectly through full `decidePlayerAiAction` runs elsewhere, no dedicated file). Real `Mission` instances throughout, same house style as `objectiveAwareness.test.ts` and `maserLance.test.ts`'s own `quietMission` — the whole point of this function is that it asks the engine for cone geometry instead of re-deriving it, so a hand-built fake context would test nothing about whether that wiring actually works. Five tests: the refusal gates (no ability / no action / no charge), EASY never firing it, holding the charge below `strikeMinTargets`, picking a clean 2-hostile cone over a higher-count 3-hostile cone that has a friendly standing in it (the case that actually proves the friendly-avoidance gate is doing something, not just picking the top score), and a full `decidePlayerAiAction` → `Mission.maserLanceStrike` round trip confirming the AI's own chosen tile is a real, engine-legal direction that actually spends a charge.

## What this does NOT cover
