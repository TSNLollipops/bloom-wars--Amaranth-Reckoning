## What shipped

**`dischargePilot(state, pilotId)`, `engine/campaignState.ts`, new §6b.** The player's own release valve for a bad pairing the Toxic Pairs Stress bleed / Anger Blowup never let go of on its own — matches permadeath's cost exactly, per the proposal's own words: the discharged pilot's `personalPoints` are zeroed (discarded, not transferred) and their `tier`/mek investment simply stops being reachable once their `CampaignPilotEntry` leaves the active roster, the same mechanism `applyPermadeathCheck`/`applyMissionLosses` already use. No cooldown, no use limit (Maxime: "No limit (Recommended)") — the cost alone is the brake.

**A new `PilotStatus` value: `"discharged"`, distinct from `"reassigned"`.** Both currently read almost identically to every system that only checks `!== "active"`, but they mean different things — `"reassigned"` is a forced departure the CO resolves after an Insult Tier-3 standoff; `"discharged"` is the player's own administrative choice, issued directly from the shop, no conversation involved. Kept apart now so the distinction survives into the proposal's own still-undesigned "bigger narrative beat" and any future House Amaranth reserve-pool reuse, rather than blurring two different departures into one value and hoping nobody needs to tell them apart later. Same safety argument the "reassigned" addition already proved out: every status check in this repo is either `=== "active"` (safely excludes a fourth value) or an exact `=== "permanently_lost"` match — verified directly against the current file (every call site listed below), not assumed from the existing comment alone.

**Commander exemption.** Refuses on `PilotRecord.exemptFromPermadeath` — the same data-driven flag `evaluatePermadeathCheck` itself checks (Rourke in Warden, her House Amaranth counterpart), not a hardcoded pilot id. The Shop UI doesn't even draw the control for this one pilot, since it can only ever fail.

**A real bug in the proposal's own reasoning, caught before it shipped, not after.** The proposal says discharging the roster's last living Munti is safe because `checkMuntiGuarantee` already exists as a free, automatic replacement. True — but `checkMuntiGuarantee` is only ever called from `Debrief.ts`, at the end of a mission. A Hub-side, shop-driven discharge has no upcoming debrief to trigger it, and `canLaunchMission` already refuses to launch **any** mission without an active Munti in the deploying squad. Discharging the roster's last one from the shop, with nothing else done, would have soft-locked a real campaign: no Munti to deploy → can't launch → can't reach a debrief → the guarantee that was supposed to save this never fires. Caught by tracing `canLaunchMission`/`checkMuntiGuarantee` against their real call sites before writing `dischargePilot`, not by trusting the proposal's own description of the safety net. Fixed by having `dischargePilot` call `checkMuntiGuarantee` itself, immediately, right after the status flip — the same free, guaranteed replacement the proposal already describes, just triggered the moment it's actually needed instead of a debrief that would never come.

**Shop UI, `scenes/shop/ShopPanel.ts`.** A `[ discharge ]` / `[ CONFIRM DISCHARGE ]` / `[ cancel ]` arm-then-confirm control on each pilot's own card (Maxime: "worth a confirm prompt so it's not an accidental click") — deliberately **not** a new list-style section next to Discretionary Recruiting the way the proposal's own phrasing first suggested. That would need a variable, roster-sized list (up to 10 pilots by Act II) inside this panel's fixed-per-entry-type row-height/pagination system, exactly the kind of unpaged, growing list the Recruit section's own candidate list is deliberately capped at 4 to avoid. One pilot's own row is a fixed size regardless of roster size, and this card already has every other per-pilot action on it (tier upgrade, loadout secondary, weapon branches, convert-to-company) — discharge belongs with them. Placed in the one strip the card had left empty (below the name/subline, above the tier-upgrade button), confirmed by re-reading `drawPilotRow`'s own layout math rather than guessing there was room. Two separate text objects for CONFIRM and cancel, not one text object sliced by click x-position — this project's own Shop-row collision from earlier today (Convert-to-company) came from exactly that kind of guessed pixel math, and two real objects with their own bounding boxes can't drift out of sync with each other. Post-discharge feedback (including the Munti-replacement note, when it fires) surfaces as an info line under the "PILOTS — PERSONAL SHOP" header, reusing the existing `info` entry type — the discharged pilot's own row is gone by the next render (no longer `status === "active"`), so the message can't live there the way `recruitMessage` lives inside the Recruit row.

**Codex / service record.** `data/codex.ts`'s `LivePilotStatus` gains a `{ kind: "discharged" }` case with its own copy, distinct from the reassigned line. `scenes/Codex.ts`'s `liveStatusFor` maps the new status through.

## Honestly still open

- **Nobody has watched this render or click in a real browser.** The layout math (the empty strip between the subline and the tier button, the "[ cancel ]" x-offset clearing the confirm text) is checked against the real current file's own coordinates, not against a live screenshot — the exact gap this project's own "a clean arithmetic check is not the same as a real click" lesson (the Combat Medic Shop-row collision, same day) warns about. Worth a real click-through next time Maxime's in the shop with more than one active pilot.
- **The reserve pool / House Amaranth reuse is deliberately not built**, per the proposal's own §3: "the discharge mechanic itself could plausibly ship with just 'goes to a reserve list' and no cross-campaign plumbing at all, with the House Amaranth reuse arriving later once that campaign is real." A discharged pilot's record simply stops being reachable from the active roster today — there is nowhere else it goes yet, same as a permanent loss.
- **The narrative closure beat is not designed**, per the proposal's own §3 ("Bigger narrative beat" — Maxime's own answer, direction only, not a finished design) and per this project's own rule against guessing content that wants a real voice. Today, discharging a pilot is silent beyond the shop's own feedback line — no scene, no line, no acknowledgment from the crew.
- **The Munti-replacement fix is the one piece of this build that wasn't in the original proposal at all** — worth Maxime's own eyes on the reasoning above (the `checkMuntiGuarantee`/`canLaunchMission` call-site trace), since it's a real behavioral difference from what the proposal describes, even though it's strictly a safety improvement, not a scope change to what discharge itself does.
- **Every other newly-active pilot (a fresh Munti replacement, in particular) is subject to the same "nobody's watched this yet" gap** every generated recruit already carries — nothing about this build changes that.
