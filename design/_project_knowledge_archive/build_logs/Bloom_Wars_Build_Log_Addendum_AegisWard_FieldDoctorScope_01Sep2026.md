## Aegis Ward — shipped, verified, committed

Munti's second Weapon Branch. The passive AoE regen aura (`engine/mission.ts`'s `tickMuntiRegen`, radius/amount in `data/combatTables.ts`'s `MUNTI_REGEN_RADIUS`/`MUNTI_REGEN_PER_TURN`) already existed campaign-wide; this branch scales the radius for whichever Munti actually owns and has it equipped — exactly the plan's own prediction ("Munti already has this aura; this just scales an existing number").

**New constant:** `AEGIS_WARD_REGEN_RADIUS = MUNTI_REGEN_RADIUS + 1` (`data/weaponBranches.ts`) — derived, not a fixed absolute, same "+1 over the baseline" convention `RAPID_RESPONSE_REPAIR_RANGE` already uses over `DEFAULT_REPAIR_RANGE`, so a future baseline-radius change keeps this branch meaningfully better rather than converging with it.

**Per-unit, not squad-wide.** `tickMuntiRegen()`'s in-range check now reads each Munti's own `weaponBranchId` — a Munti with Aegis Ward equipped projects the wider radius, a second Munti in the same squad without it still projects the plain one. Mirrors the exact pattern Rapid Response already uses for repair range.

**Munti is now a real multi-branch path**, same shape Reeps already exercises (Missiles then Rail Lance): Aegis Ward is gated as Munti's 2nd purchase (tier C, `WEAPON_BRANCH_COSTS[1]` = 220), same purchase-order-not-branch-identity rule the whole system already runs on. The Shop and Transporter Pad UI needed zero changes — both were already fully generic off `WEAPON_BRANCHES_BY_PATH`/`ownedWeaponBranches`, confirmed by reading `ShopPanel.ts` and `TransporterPad.ts` before assuming so.

**Test coverage:** `engine/__tests__/muntiRegen.test.ts` (radius extension + regression guard) and `engine/__tests__/campaignEconomy.test.ts` (2nd-branch tier/cost gate, mirroring the existing Reeps case).

## Field Doctor — shipped, verified, committed

The plan doc's original framing — "cheaper Repair, or an extra Repair charge per mission" — didn't survive contact with the live `repairUnit()`: Repair has no cost and no charge cap to begin with, flat 1-of-2-actions, unlimited uses. Nothing to make cheaper, no existing budget to extend. Raised directly, with two concrete alternatives that stayed true to the branch's stated identity ("more repairs, not stronger ones," the inverse of Combat Medic). **Maxime's call: a free Repair every N turns** — the option that actually matches the plan's own "same shape as Weapons Bay's bonus Fire Support charge" comparison (that charge is itself cooldown-gated, not a flat add-on).

**Mechanism, built on real existing scaffolding, not new infrastructure:** `BattleUnit.abilityCooldowns` — typed and initialized on every unit since 28 Aug, but per `engine/cooldown.ts`'s own header comment, never actually written to by any ability until now. Field Doctor is the first ability to use it. `FIELD_DOCTOR_COOLDOWN_TURNS = 3` (`data/weaponBranches.ts`) — deliberately the same value as `WEAPONS_BAY_FIRE_SUPPORT_COOLDOWN_TURNS`, matching the plan's own comparison exactly rather than picking an unrelated number. A new `fieldDoctorBonusReady()` check (true when the branch is equipped AND the cooldown, tracked under the real `"abil_repair"` key, is elapsed) gates both `getRepairableFrom()` (what the UI offers as a target) and `repairUnit()` (the actual verb), so the two can't drift the way `DEFAULT_REPAIR_RANGE`'s own history already warned against. Baseline actions are always spent first — the free bonus only fires once `actionsRemaining` is already 0, then goes on cooldown for `FIELD_DOCTOR_COOLDOWN_TURNS` turns. Same "baseline pool spent first" shape as the Weapons Bay's own bonus Fire Support charge.

**A second, real bug found and fixed in the same pass — not a new feature, a reachability gap.** The engine-level logic above was correct and passing tests the moment it was written, but a live check against the actual player-facing UI (`scenes/Battle.ts`) found it would have been completely unreachable through real play: two separate selection guards — the Tab-cycle-to-next-unit filter and the primary click-to-select handler — both excluded any unit with `actionsRemaining <= 0` from being selectable at all, and a third spot (`refreshSelectionAfterAction`, which runs after every Move/Repair/Sensor Sweep/Screen) deselected a unit the instant its actions hit 0. Since Field Doctor's entire point is "repair once more after your normal actions are gone," a Munti who'd already spent both actions would never have been clickable again — the free repair would have sat correctly in the engine and never once been reachable by a mouse click. Fixed by adding a public `Mission.fieldDoctorReady(unitId)` wrapper and reading it, alongside the existing `actionsRemaining > 0` check, in all three spots. Also added one HUD status line ("FIELD DOCTOR — one free Repair ready") so "0 actions left" doesn't read as "nothing more to do" when it isn't. Caught by checking the real UI path before calling this done, not by a test — worth flagging as a genuine near-miss: engine-correct and 100% test-green is not the same thing as player-reachable, and this project's own emphasis on checking neighbors after a fix is exactly what surfaced it (checking what's around `repairUnit()` meant checking who calls it, not just the function itself).

**Test coverage, new:** six cases added to `engine/__tests__/repair.test.ts` (baseline-actions-spent-first, the free repair firing at 0 actions, no leak without the branch equipped, the bonus going on cooldown after use, the cooldown actually elapsing after `FIELD_DOCTOR_COOLDOWN_TURNS` turns, and `getRepairableFrom` only offering a target at 0 actions while the bonus is genuinely ready) plus one in `engine/__tests__/campaignEconomy.test.ts` (Munti's 3rd-branch tier/cost gate, tier B / `WEAPON_BRANCH_COSTS[2]`).

## A separate, unrelated finding surfaced while verifying this pass — now resolved

Running `npm run sim` (Team One's archived `MISSION_1A`, used only to confirm the build didn't crash) printed a Team One pilot with an anomalous single-word display name — the only pilot in that roster without a full "First Last" name, everyone else being Hiro Nagori, Yren Tourignie, Fracrals Thyns, Derek Barasj. That name matched one of the Build Brief's reserved terms from the book series. Flagged rather than silently renamed, and Maxime confirmed it directly: it is a lock term.

**Fix, done and committed:** renamed to **Marcus Voss** across every occurrence — `pilot_trav`/`mek_trav` IDs became `pilot_voss`/`mek_voss` (`src/data/meks.ts`, `src/data/campaign.ts`, and the `pilot_voss` fixture already in `src/engine/__tests__/overwatch.test.ts`), plus comment-only provenance references in `src/data/types.ts`, `src/data/crewBanterSlots.ts`, and `src/engine/campaignState.ts`. Also swept the repo's own `design/` planning docs (not just the claude.ai Project docs) and found three more real hits: `design/Bloom_Wars_Spitball_Ideas.md`, `design/Consolidated_Build_Plan_Progress.md`, and `design/Bloom_Wars_Crew_Banter_Phrase_Bank_v1.md` — the last of which described this character's personality as written "per his own established book-canon voice," which both confirmed the correct pronoun and meant the fix needed a name that reads as male (a first-pass rename was caught and corrected before it reached this doc, precisely because that line named the pronoun and the first attempt didn't match it). The "book-canon voice" phrasing itself was also softened to plain trait description rather than a direct pointer at the source — the traits (reserved, quiet, non-reflective, warms slowly) stay, since a character's personality isn't itself a locked term, but naming where it came from is closer to the line the lock is meant to hold.

Kept the surname "Voss" (already the internal ID) across the correction to keep the blast radius small. Full verification suite re-run clean after the correction: `tsc`, `eslint`, `vitest` (1204/1204), `build`, and `sim` all pass, with "Marcus Voss" printing correctly in sim output. All 6 files re-committed to the device with zero conflicts.

One open question left for Maxime, not resolved here: whether this pilot's *personality* (reserved, quiet, warms slowly) was deliberately written as a direct import of the book character's voice, and if so whether that's worth revisiting on its own terms, separate from the name fix. Not touched unilaterally — a bigger creative-continuity call than a rename.
