## 1. The six new verbs

All six live in `src/data/verbs.ts` (`VerbId` union + `VERBS` record, `broadcast: false`, no fixed `outcome` — same shape as the existing `pegBoard`/`askOut` precedent) and are recognized by six new keyword buckets in `src/data/chatIntent.ts`'s `VERB_REQUEST_KEYWORDS`. Content — reaction lines, deltas, thresholds — lives in a new module, `src/data/socialActions.ts`.

- **Gift** — "gift" / "give a gift" / "brought you something" / "got you something" / "here's a gift". A flat Favorability bump (`GIFT_FAVORABILITY_DELTA = 4`) plus a catalyst-flavored acceptance line (`pickGiftLine`). Live-verified: `+4` Favorability, "Didn't have to do that. Appreciate it — good for morale too."
- **Praise** — "well done" / "great job" / "good work" / "proud of you" / "you did great" / "you're doing great" / "nice job". Also `+4` (`PRAISE_FAVORABILITY_DELTA`), symmetric with Gift, per-catalyst line via `pickPraiseLine`.
- **Insult** — "stupid" / "idiot" / "useless" / "worthless" / "pathetic" / "screw you" / "shut up". A per-catalyst negative delta (`INSULT_FAVORABILITY_DELTA`, a `Record<Catalyst, number>`, not a flat constant — matching the proposal doc's own §4 table: insult should sting harder for some catalysts than others), an `insultsGiven` lifetime counter that never resets, and the three-tier escalation ladder in §2 below.
- **Apology** — "sorry" / "i apologize" / "my apologies" / "i shouldn't have said that" / "forgive me" / "i take it back". A per-catalyst positive delta (`APOLOGY_FAVORABILITY_DELTA`, matching the proposal doc's own §4 "forgives... easily / hard / rarely" table) — repairs Favorability but never decrements `insultsGiven`; the historical fact of an insult having happened doesn't un-happen, only its standing damage is repairable, exactly as the proposal doc's §1 specified.
- **Congratulate** — "congrats" / "congratulations" / "well earned" / "you earned that". Gated on a real, live `"promoted"` HotTopic actually existing for that pilot — asking with nothing to congratulate gets an honest **"Congrats for what?"** rather than a silent generic bump. With a real topic live: `CONGRATULATE_FAVORABILITY_DELTA = 5`, `CONGRATULATE_MORALE_DELTA = 6`, plus a `pickCongratulateLine` reaction. Live-verified both paths: the no-topic case returned exactly "Congrats for what?"; pushing a real `promoted` topic first and asking again returned a real reaction line and the expected deltas.
- **Send-Off** — "wish me luck" / "watch my back out there" / "look out for me out there" / "send me off". `SEND_OFF_FAVORABILITY_DELTA = 3`, `SEND_OFF_STRESS_DELTA = -6` (a small immediate stress relief for the pilot being sent off), plus setting `CampaignState.preMissionSendOff = { pilotId, grantedAt }`. That field is intentionally unconsumed this pass — see §5, "Honestly still open."

All six resolve through a new private `Hub.ts` method, `resolveChatTarget(raw, requireRoom?)`, which tries `extractNamedTarget` first (see §3) and falls back to the existing `nearestNpcInRange(APPROACH_RADIUS, requireRoom)` — the same two-tier "named, else nearest" shape `askOut`/`pegBoard` already established, just generalized into one shared helper instead of six copies of the same fallback logic.

## 2. The Insult escalation ladder and the Tier-3 CO resolution

Three tiers, matching the proposal doc's own §3 shape, with placeholder numbers throughout (same discipline as every other new social-sim number this project ships with — Antfarm bay costs, the original Wellroot `attackPower` — needs playtesting, not a sim script, since there's no `combat_sim.py`-equivalent for social pacing):

- **Tier 1 — every single Insult.** The per-catalyst Favorability hit plus an immediate reaction line (`pickInsultLine`).
- **Tier 2 — at `insultsGiven >= INSULT_TIER2_COUNT` (3).** A `+10` Stress bump (`INSULT_TIER2_STRESS_BUMP`) and a real `"insulted"` HotTopic registered through the already-built `hotTopics.ts` engine — no new plumbing, a new topic kind slotted into the existing system exactly as the proposal doc predicted it could be. Live-verified: after the 3rd insult, `insultsGiven: 3`, Stress `10 -> 20`, and a real `{kind: "insulted", aboutPilotId: ..., aboutName: "Spec. Corin Lask", ...}` HotTopic found live in `hub.hotTopics`.
- **Tier 3 — at `insultsGiven >= INSULT_TIER3_COUNT` (6) AND current Favorability still at or below `INSULT_TIER3_FAVORABILITY_CEILING` (-10).** The Favorability-ceiling condition is what makes this recoverable in practice, not just in theory: a player who's been apologizing and rebuilding trust between insults never gets blindsided here even at a high lifetime count, exactly the proposal doc's own §3 reasoning for using a counter *and* a live threshold together rather than either alone. When both conditions hold, `HubPilotSocialState.refusesDeployment` flips permanently true and `TransporterPad.ts`'s squad-assembly roster filter (`activePilotIds`) excludes that pilot from deployment: `entry.status === "active" && !entry.social?.refusesDeployment`. Live-verified: after the 6th insult, `insultsGiven: 6`, Favorability `-48` (well past the `-10` ceiling), `refusesDeployment: true`.

**The CO call-out.** The first time the CO (`npc_co`) is Talked to after a pilot enters the Tier-3 standoff, he raises it unprompted, once, gated by a new `coCalloutGiven` flag so it never repeats: *"Before you say anything else — Spec. Corin Lask came to see me. Says they won't fly with you anymore. That's not something I can wave off."* Live-verified via a real E-key Talk press standing on the CO, not a direct method call.

**The resolution itself — the one piece Maxime's own answer required that neither of the proposal doc's own options needed: the player has to explicitly ask the CO to remove the refusing pilot.** A new `detectRemovePilotIntent` keyword bucket in `chatIntent.ts`, checked in `submitChat()`'s CO-gated precedence chain (same "must be near the CO, else redirect" pattern the existing debrief-request/build-request checks already use), routes to a new `handleRemovePilotRequest` method. It sets `PilotStatus` to a new third value, `"reassigned"` (alongside the existing `"active"`/`"permanently_lost"`), sets `refusesDeployment` back to false (moot once the pilot is gone, but keeps the record internally consistent), and removes the NPC from `hub.npcs` for the rest of the session. Apology alone can never reach this state or undo it once it's reached — the standoff is real, and its only exit is the specific action Maxime named. Live-verified: `"I want to remove them from the ship"` → CO replies *"Done. Spec. Corin Lask's reassigned off the ship, effective now. Hope it was worth it."* → `PilotStatus` reads `"reassigned"` → the pilot count in `hub.npcs` drops by exactly one.

`PilotStatus` gaining a third value was audited across the full repo before shipping (every existing `=== "active"` / `=== "permanently_lost"` check, and everywhere `PilotStatus` is switched over) to confirm nothing silently mishandles the new state — the type-checker itself catches an unhandled-case switch, but every comparison-style check was still hand-verified to fail closed (i.e., a `"reassigned"` pilot reads as not-active everywhere that matters — roster rosters, deploy eligibility, mission assignment) rather than accidentally falling through as if still active.

## 3. Named chat targeting — designed for six verbs, and a real bug it exposed

A new `extractNamedTarget(raw, candidates)` in `chatIntent.ts` lets any of the six new verbs (plus a re-check against the existing ones) resolve to a *specific* NPC by name rather than only "whoever's nearest" — "well done, Corin" now reaches Corin specifically even if someone else is standing closer. It matches word-for-word tokens of a candidate's `displayName` (case-insensitive, word-boundary-anchored), picking the longest matching word across all candidates as the best match.

**A real production bug was found and fixed via this pass's own live-browser verification, not a unit test.** The first live run of the new Playwright script (`tools/verify/checkSocialActions.mjs`, see §4) tried praising a specific named pilot by her rank abbreviation and got `namedTargetDeltaA: 0, namedTargetDeltaB: 0` — a completely different, third NPC responded instead. Root cause: `extractNamedTarget`'s first version *stripped punctuation* from each word of a display name (`word.replace(/[^a-zA-Z]/g, "")`) rather than dropping rank-prefix tokens entirely — so `"Spec."` became the bare word `"Spec"` and was treated as a legitimately matchable name. Since many pilots share a rank ("Spec. Corin Lask", "Spec. Elin Vashti," and others), any chat line that happened to contain a shared rank word could false-match the wrong pilot. Fixed to mirror `scenes/TransporterPad.ts`'s own already-established `pilotInitials()` convention exactly: filter candidate words to `/^[A-Za-z']+$/.test(w)`, i.e. drop any word containing a digit or period *entirely*, rather than stripping the punctuation and keeping what's left. Two new regression tests were added to `chatIntent.test.ts` pinning this exact failure mode (a rank-only fragment must never resolve; a real given name or surname must). Re-verified clean afterward: `namedTargetDeltaA: 4, namedTargetDeltaB: 0` — the named pilot moved, the bystander standing right next to her didn't.

Worth stating plainly, matching this project's own "verify against the actual current file, not memory" discipline: this bug would not have been caught by typecheck, lint, or the pre-existing unit test suite alone — it took driving the real chat UI in a real browser against two real, similarly-ranked NPCs to surface it.

## 4. CO Confide — the grotto stress-relief hook, finally built

`Bloom_Wars_Antfarm_Carrier_Hub_v1.md` §11.3 flagged a "Confide" interaction with the CO as a concept back when the grotto first got him seated — never built until Maxime's **"the other thing good too."** A new `detectConfideRequest` keyword bucket, gated the same CO-proximity way as the debrief-request and build-request checks, routes to `handleConfideRequest`. The CO's line is a real, dedicated bespoke line (`pickCoConfideLine`, not a fallback to the generic ambient pool) — *"Get it off your chest. Nobody else needs to hear this but me."* — and it moves `CampaignState.mcStress` down by `CONFIDE_STRESS_DELTA` (-15).

**This is the first real slice of Rourke's (the MC's) own persisted state.** `CampaignState.mcStress` is new (`mcStress?: number`, default `MC_STRESS_DEFAULT = 40` when first read), and Confide is its only mutator this pass — nothing else reads or writes it yet, deliberately (see §5). Live-verified: `mcStressAfter: 25`, `mcStressDelta: -15`, matching the constant exactly.

## 5. Honestly still open

- **Send-Off's actual tactical payoff is deferred.** `CampaignState.preMissionSendOff` is set for real (pilot id + timestamp), but nothing on the Battle side reads it yet — no forecast bonus, no morale-on-deploy effect, nothing. This is a deliberate half-shipment: a real Battle-side bonus needs its own `combat_sim.py`-validated number, the same discipline every other combat-facing stat gets, and that tuning pass hasn't happened. The Hub-side ritual (the chat line, the Favorability/Stress deltas, the flag itself) is real and complete; the tactical half is the honest remainder.
- **Every new numeric constant in `socialActions.ts` is a first-guess placeholder, not a sim-validated or playtested number** — `GIFT_FAVORABILITY_DELTA`, the per-catalyst Insult/Apology tables, the Tier 2/3 thresholds, `CONGRATULATE_MORALE_DELTA`, `SEND_OFF_STRESS_DELTA`, `CONFIDE_STRESS_DELTA`, `MC_STRESS_DEFAULT`, all of it. Same "flag rather than pretend it's locked" discipline this project already applies to Antfarm bay costs and the original Wellroot `attackPower` guess — worth a direct playtest pass once Maxime has actually lived with these numbers in a running campaign.
- **`mcStress` has exactly one mutator (Confide) and zero consumers.** It doesn't decay, doesn't feed into any other system yet, and nothing reacts to it being high or low. This pass's scope was "give the MC her own state, and one thing that moves it" — a fuller MC-stress system (ambient triggers, a UI readout, consequences at high stress mirroring the crew's own Stress/Morale work) is a real follow-on, not started here.
- **`insultSocialAfterCallout` and `coCalloutGiven` were verified for the standoff's first pilot only** — the live-verification pass drove exactly one pilot through the full Tier-1→Tier-3→callout→removal pipeline, not a second concurrent standoff. Nothing in the code path is pilot-count-limited (the gates all key off that specific pilot's own `HubPilotSocialState`), but two simultaneous refusing pilots hasn't been observed running together.
- **The "Loadout" naming and a few other adjacent judgment calls from earlier passes remain their own separate open items** (unrelated to this pass, carried over from the Mek NPC Introduction section of the Master Index) — not touched or affected by anything here.
