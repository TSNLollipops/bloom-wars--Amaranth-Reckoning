## 1. NPC Conversation Lock Fix

Root cause confirmed exactly as the proposal traced it: `showBubble()` only sets an NPC's own `bubbleUntil` the instant a bubble actually appears. For the second half of a staged two-line exchange, that's `NPC_REPLY_DELAY_MS` (1800ms) in the future — and neither `updateNpcRoaming()` nor `updateNpcEncounters()` had any reason yet to leave that NPC alone during the gap. `ROAM_INTERVAL_MIN_MS` is 5000ms, shorter than the ~7800ms an exchange actually needs to finish, so this was a real, reachable bug, not a theoretical one.

**Built:** `HubNpc.engagedUntil?: number`, set to `now + NPC_ENGAGEMENT_HOLD_MS` (a flat `NPC_REPLY_DELAY_MS + BUBBLE_DURATION_CAP_MS` = 7800ms) by all three encounter-staging functions — `runNpcEncounter()`, `runAngerBlowup()`, and `runBoredomSpar()` — for BOTH participants, unconditionally, regardless of which branch actually fires. Checked via a new `isNpcEngaged()` guard at the top of `updateNpcRoaming()` (before even the journey-resume branch, same priority `mustered` already gets) and in both of `updateNpcEncounters()`'s own pairing guards.

**Read `tryBoredomSpar()`/`runBoredomSpar()` for the first time this session** (the proposal explicitly flagged it as unread). Found it only ever shows ONE bubble, on npcA — no delayed second line the way the "talk" kind and Anger Blowup both get. npcB is held anyway, for consistency with `runNpcEncounter()`'s other single-bubble kinds (pegBoard/poker/fletchers/askOut), which get the same blanket treatment for the same reason: one rule for "an encounter is in progress," not a special case per branch depending on who does or doesn't get a bubble.

**Checked and found currently redundant, kept anyway:** the two `updateNpcEncounters()` guards. `ENCOUNTER_COOLDOWN_MIN_MS` (12000ms) already exceeds `NPC_ENGAGEMENT_HOLD_MS` (7800ms) with real margin, so a third ant pairing with an already-engaged NPC was already blocked by the existing `nextEncounterAt` cooldown before this fix. Added the `engagedUntil` check there anyway, documented as belt-and-suspenders — the alternative was leaving correctness resting on an unenforced, unlabeled invariant between two unrelated tuning constants that could drift apart later without anyone remembering why it mattered.

**Fix B (facing each other) — confirmed out of scope, not built.** Grepped `Hub.ts` for `flipX`/`facing`/`setFlip` per the proposal's own instruction: zero hits outside the English word "player-facing" in comments. There is no sprite-orientation concept anywhere in this file. Worse than "bigger than it looks" — NPCs render as plain `Phaser.GameObjects.Arc` circles (no directional art at all), so "face each other" may not even be visually meaningful without a shape change first, not just new logic. Flagging back rather than guessing at scope, per the proposal's own instruction.

**Test coverage, and an honest note on why it's narrow:** `isNpcEngaged()` (the exact boolean the fix hinges on) is unit-tested — 4 cases in `src/data/__tests__/npcEngagement.test.ts`. It does NOT live in `Hub.ts` itself: the first attempt at that (as `Hub.ts`'s first-ever named export) broke immediately — `npx vitest run` threw `ReferenceError: window is not defined` from Phaser's own OS-detection code, which runs at module load time. No test had ever imported a `scenes/*.ts` file directly before this, so nothing had hit that wall until now. Moved the one-line predicate to a new dependency-free `src/data/npcEngagement.ts` instead, matching this file's own established "scenes/** composes, data/** decides" split. `updateNpcRoaming()`/`updateNpcEncounters()` themselves remain untested — same as the rest of `Hub.ts`, which has zero scene-level test coverage today. **Live verification (watching two ants actually hold still through a full staged exchange in a real Hub session) has not been done and is the real proof this fix works end to end.**

## 2. Hub Floor Portrait Revert

Built exactly as scoped: `drawPilotAvatar()` (`TransporterPad.ts`) takes a new 9th parameter, `forcePlaceholder = false`. Default false means the four other call sites (Transporter Pad, RosterPanel, MemorialPanel, Debrief) are byte-for-byte unaffected — confirmed via `tsc --noEmit` after the change, and by grep showing those three files' own `drawPilotAvatar()` calls untouched.

`Hub.ts` passes `true` at every avatar it draws on the floor — **five call sites, not the three the original proposal named.** The proposal covered the pilot-NPC roaming loop, the CO, and the player; it didn't account for the two Mek workshop loops (`buildNpcs()`'s two Mek-seeding blocks), which also draw floor avatars via the same function. Added `forcePlaceholder: true` there too, for consistency — currently a no-op visually (Mek ids never match a portrait key, so they were always placeholder already), same "insurance against a future addition, not a behavior change today" reasoning the CO's own call site already used.

Not touched, on purpose: the art pipeline, `portraits.ts`'s id resolution, the 12-portrait generic-recruit mapping, or any of the four other scenes' real-portrait rendering. **Not yet visually confirmed live** — this is a pure code-level "same shape as before B4" argument, not a screenshot comparison.

## 3. Worries System — build order step 2

Scoped exactly to the proposal's own step 2: "read-side only, wire into `pickSoloEcho`'s existing chain, ambient dialogue content, nothing else." Did NOT touch: the `mission.ts` combat bridge (step 3), the domestic bucket (step 4), or any Stress/Morale write-back (step 5, explicitly deferred).

**New module, `src/data/worries.ts`:** `WorryEntry` (source/catalyst/intensity/bornAt/expiresAt), `upsertWorry` (insert-or-refresh per source, fixed `WORRIES_STACK_CAP = 4`, weakest bumped once a NEW source would overflow it), `removeWorry` (explicit, for Mission Worry's own instant-clear case), `pruneExpiredWorries`, `loudestWorry` (Gate 3's "loudest thing wins" rule). 13 unit tests in `src/data/__tests__/worries.test.ts` covering the cap/eviction rule, explicit removal, expiry pruning, and the loudest-pick. `AnimalTag` is `Catalyst` re-exported under its own name (same 9-entry vocabulary, explicitly not a new taxonomy, per the proposal) — a type-only re-export, so no runtime circular import between `worries.ts` and `ambientLines.ts` despite each needing a type from the other.

**Mission Worry absorbed as the first live source**, in `Hub.ts`'s existing `updateMissionWorry()` (same per-NPC `nextWorryCheckAt` cadence, same `worryTriggerChance()` math, unchanged). On each check: computes `intensity = worryTriggerChance(elapsedSinceOnset, favorability)` directly (no longer just a coin-flipped boolean) and upserts/removes a `mission_pilot_missing` `WorryEntry` on the NPC's own `worries` list, then reads `loudestWorry()` into a new `ambient.topWorry` field.

**Deliberately kept `ambient.worried: boolean` completely unchanged** — still computed by its own independent `Math.random() < intensity` roll, still what `reactionGate.ts`'s `GATE0_WORRY_BONUS` and the roster panel's "Worried about someone on mission" line both read. Out of scope for this pass (Breakdown/roster panel aren't "ambient dialogue content"). This means `worried` and `topWorry` are now two INDEPENDENTLY-ROLLED samples of the identical underlying intensity, and can disagree at any single instant — flagged explicitly in both the code comments and here, not something to be surprised by later. `pickSoloEcho` (`ambientLines.ts`) now checks `topWorry` (rolling fresh against its live intensity every time a line is actually picked) instead of the old boolean; same fear echo, same `LINE_BANK` content, `reason` is now the entry's own source id (`"mission_pilot_missing"`) instead of the hardcoded string `"worried"`.

**Judgment call worth a gut-check, not decided unilaterally:** tagged Mission Worry's `WorryEntry.catalyst` as `"wolf"` (teamwork). The proposal doesn't pin this down for this specific source — it only says reuse the 9-animal vocabulary, not which one. Grounded in `ambientLines.ts`'s own pre-existing comment, which already cites the wolf catalyst's fear-bank lines ("Don't scatter... we lose someone else," "Sound off, I need to hear every voice") as reading like crewmate-worry as much as self-panic. Doesn't drive any visible behavior today — `pickSoloEcho` keys content off the PILOT's own catalyst, not the worry's — so this is forward-looking metadata for the step 3 combat bridge, worth confirming with Maxime once that's actually built, not a blocker now.

**Known, accepted gap:** `topWorry` is NOT seeded at NPC construction time the way `ambient.worried` is (the five `ambient: {...}` object literals in `Hub.ts` still eagerly compute `worried: isMissionWorrySignal(...)` for first-frame correctness, per B4-era comments). `topWorry` starts `undefined` until the first `updateMissionWorry()` tick runs. Left as-is deliberately — the edge case is an ambient line firing in the literal first frame, before any update tick, while a mission attempt is also already active past onset. Narrow enough not to justify touching five more call sites for this pass; flagged rather than silently accepted.

**Docs the proposal itself flagged as needing an update once this is picked up, not yet done:** `Social_Sim_Roadmap_v1.md` #8 should note Mission Worry is now absorbed/superseded rather than standing as its own independent feature; `NPC_Reaction_Engine_v1.md` §4a should point at Worries as the actual landing spot for the combat bridge it already describes.
