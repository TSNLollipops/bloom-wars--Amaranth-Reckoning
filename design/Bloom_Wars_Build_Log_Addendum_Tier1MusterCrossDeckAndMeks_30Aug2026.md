## Addendum, 30 Aug 2026: Tier 1 (partial) — muster's two real bugs: cross-deck routing, and Meks/CO answering a pilot-only call

Consolidated Build Plan (29 Aug 2026), Tier 1, items #3 and #4 (of four Hub collision/movement bugs in that tier — see "Still open" below for the other two, which this pass did not touch). Maxime: "fait tout en batch. 1 a la fois. jusqua ske tu manque de credit."

**Root cause, both bugs, confirmed against the actual code.** `sendToMuster` (`scenes/Hub.ts`) predates the Hub's multi-deck Antfarm Grid entirely — its own header comment is dated 26 Aug 2026, "Rec-Room-only... every NPC in this pass" — and was never revisited when 27 Aug's Grid pass added real decks, or when 29 Aug's Mek Introduction Plan gave Meks the exact same roaming/movement code as deployable pilots. Two separate, compounding gaps fell out of that:

1. It set `targetX`/`targetY` straight to the single fixed `MUSTER_POINT` coordinate regardless of which deck the NPC was actually standing on. Free-roam movement never crosses a deck on its own (`tryMoveNpc`'s own comment) — only the door-hop machinery (`travelTargetRoom`/`completeDoorHop`) does, and `sendToMuster` never touched it. An NPC mustering from Upper or the Grotto would walk toward whatever that raw pixel coordinate happened to land on within their OWN current deck's floor, arrive at the wrong place, and just stop.
2. It had no notion of "can this unit even deploy." Meks were deliberately given the identical roaming code real pilots use (Mek NPC Introduction Plan v1, 29 Aug — "Otherwise they can roam") specifically so every generic Hub system would pick them up for free; muster is the one system that should NOT have picked them up, and nothing carved out the exception.

**The fix, reusing what already existed rather than building a parallel system.** `sendToMuster` now: (a) checks `this.campaignState.pilots[npc.pilotId]` first and returns immediately if it's not a real, active, deployable pilot — a Mek's `HubNpc.pilotId` is its own mek id ("mek_rourke"), never a key in that table, so this excludes every Mek for free with no string-prefix check needed, and incidentally closes the identical latent gap for the CO (`npc_co`), who was never reported broken but had the same exposure; (b) branches on `sameDeck(npc.room, MUSTER_ROOM)` — a new constant (`MUSTER_ROOM = "recroom"`, also now the single source of truth `isAtBay` reads instead of its own separate hardcoded literal) — same-deck musters walk straight to `MUSTER_POINT` exactly as before (recroom, hangarDeck, and berths all share the Lower deck's open floor, so this covers all three with no door involved, matching how ordinary same-deck exploring already works); a genuinely cross-deck muster instead reuses `nextHopDoor`/`travelTargetRoom`, the identical, already-proven machinery `updateNpcRoaming`'s own cross-deck explore branch has used since 26-28 Aug.

**Two follow-on gaps found and closed in the same pass, not shipped separately** — the kind of "check what's sitting immediately around a fix" the writer-side process notes call for, applied here to game code instead of prose:

- Reusing the door-hop machinery gets an NPC onto the right DECK and into the right ROOM (the door tables' own `toRoom` for every hop into Lower already resolves to exactly `recroom`), but arriving in the right room isn't arriving at `MUSTER_POINT` — a precise point inside it. Ordinary explore-roaming never needed anything past "arrived in the target room"; muster does. `completeDoorHop`'s own "arrived at the final room" branch now checks `npc.mustered && npc.room === MUSTER_ROOM` and, if true, sets `targetX`/`targetY` to `MUSTER_POINT` for the last stretch instead of leaving the NPC standing at the door they walked in through.
- `updateNpcRoaming`'s `mustered` guard used to be the very first line in its per-NPC loop — correct for its own stated purpose (don't hand a mustered NPC a fresh explore/mingle target once they've arrived) but it also blocked the SAME function's own mid-journey resume branch (the one that re-issues a target toward the next door after a stuck-timeout give-up mid-hop), which a cross-deck muster can now genuinely need. A mustered NPC stuck mid-transit would have had no path back to life — nothing else ever re-sets their target once `updateNpcMovement`'s stuck-timeout clears it, and `updateNpcRoaming` would bail on `mustered` before ever reaching the resume check. Reordered: the journey-resume branch now runs first (mustered or not — resuming an in-progress trip isn't "a new roam target," so it doesn't reopen the gap the guard exists to close), and the `mustered` check moved to right after it, still ahead of the explore/mingle logic it's actually meant to block.

Traced by hand end to end (Workshop → Grotto → Lower deck door hops, landing spot → `MUSTER_POINT`, and the stuck-mid-hop resume path) against the actual door table (`DOORS`) and deck map (`ROOM_DECK`/`DECK_ORDER`) rather than assumed correct from the shape of the diff.

**Verification.** `npm run typecheck`, full `npm test` (1139/1139, zero regressions — nothing in the suite touches `Hub.ts`, which has no dedicated tests of its own, same gap the Consolidated Build Plan's own Tier 1 entry already names), and `npm run lint`, all clean, in the same staged cloud sandbox this session's other Tier 0/1 work used (no `device_bash` this session). **What this pass explicitly does NOT have:** the real Playwright walkthrough the plan's own Tier 1 entry calls for ("standing at a clustered door, forcing a muster call from the top floor, checking a Mek doesn't respond to it") — driving the live Phaser canvas needs a running dev server and a browser session this verification pass didn't set up. The fix above is logic-traced against the actual code paths, not click-tested. Worth an actual playtest (or a dedicated Playwright pass, same shape as the door-build work's own 52-check suite) before calling this closed.
