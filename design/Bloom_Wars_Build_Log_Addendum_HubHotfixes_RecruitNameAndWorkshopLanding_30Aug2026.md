## Addendum, 30 Aug 2026: Hub hotfixes — recruit NPCs showing raw pilot ids, and a bad workshop landing point

Two real bugs Maxime caught live in the Hub and reported with screenshots mid-Tier-6, before that tier's own scope (never clearly re-derivable — see the progress log's own note on why) was settled: "hangar bug. at the top deck they spawn on the botton while the door at the top, thats pretty wier... 2cd npic is the recruit name not showing well." Both folded into this pass immediately rather than deferred, per his own "fold those check into the next pass" — small, well-scoped, and both regressions from earlier Tier 3 work in this same session, so leaving them open would mean shipping on top of a known-broken foundation.

**Bug 1 — a generated recruit's raw id ("pilot_recruit_3") rendered as their own name tag.** Tier 3's `buildNpcs()` rewrite (this session, earlier) sourced each pilot NPC's `displayName` from `findPilot(pilotId)` — `data/pilotRegistry.ts`'s STATIC index, built only from the five hand-authored roster lists (PILOTS/ROSTER_DEPTH_PILOTS/WARDEN_PILOTS/SECOND_LANCE_PILOTS/THIRD_LANCE_PILOTS). A runtime-generated recruit (`engine/campaignState.ts`'s `generatePilot`) is in none of those lists, so `findPilot()` returned `undefined` and the fallback (`pilot?.displayName ?? pilotId`) rendered the bare id straight onto the Hub floor. The Mek loop a few hundred lines below already had the right answer for the identical problem: `this.campaignState.pilots[pilotId].pilot` — the LIVE, per-campaign copy every id in `activePilotIds` is itself built from — always exists and is always complete, generated or hand-authored alike, because it's exactly the record the campaign actually assigned that pilot when they joined the roster. The pilot loop now reads displayName, archetypeId (color, romanceable-species) and tier straight off that live copy instead of the static index; `findPilot()` is no longer called from Hub.ts at all, and its import was removed. Worth naming honestly: this is the second time this exact symptom (a bare pilot id shown as a name) has appeared in this file — Tier 3 itself fixed the first case (`WARDEN_PILOTS.find()`, only 5 pilots) by switching to `findPilot()` (wider, but still static); this fix closes the same class of bug for good by switching to the one source that was never going to miss anyone, live or generated.

**Bug 2 — arriving on the Upper Deck lands you at the opposite end from the door.** `DOORS`' `grotto-to-workshop` entry (the stair from the Grotto up to the Upper Deck / Workshop) had `toY: 470` — the bottom of workshop's own zone (`y:[108,552]`) — while workshop's own return door back down (`workshop-to-grotto`) sits at `y: ROOM_BOUNDS.top + 22 = 130`, the top of that same zone. Every other same-shape door pair in this table lands you close to the door you'd use to go back (e.g. `recroom-to-grotto` lands near grotto's own down-stair, not its up-stair) — this one just never followed that rule, almost certainly a copy-paste of `recroom-to-grotto`'s own `toY` one line above without re-deriving it for a door on the opposite edge of its room. Fixed to `toY: 230` — the same "~100px offset from the destination's own stair marker" convention this file's own header comment already documents for every other pair, so arriving on the Upper Deck now lands you right next to the door, not clear across the room from it. `switchRoom`'s own `pickPointNearDoor` still jitters off this anchor and rejects overlap with whatever NPCs/Meks are actually standing there at the time (confirmed this is how it already works before touching the number), so the fix only had to be a sane anchor near the correct door, not a hand-cleared exact pixel.

**Verification.** `npm run typecheck`, `npx eslint src/scenes/Hub.ts`, and full `npm test` (1140/1140, zero regressions — `hubGeometry.test.ts` asserts the door's own trigger point, `{x:480,y:130}`, which is unchanged; nothing asserts on the landing `toY` that moved). Same caveat every Hub.ts change this session carries: logic-traced against the real coordinate system and the collision-avoidance code that actually runs at the landing site, not click-tested in a live browser — still owed, now across Tiers 1-4 plus this pass.
