# Mission 36 — Until Relief

**Objective:** survive_n_turns (turnLimit 16) [campaign finale]. **Enemy:** 6 waves.

Same knife-edge tuning sensitivity as Mission 34, a third time this batch. First-draft "biggest yet" counts (14/6/6/10/8/2, 46 total) went 0/20, every run a full wipe by turn 9-15. Cutting to 10/4/4/7/6/2 (33 total) overcorrected the other way to 20/20 win — a 39% swing in total count was enough to flip certain-loss to certain-win outright. A middle step (12/5/5/8/7/2, 39 total) landed correctly.

**Result:** 16/20 (80%) — harder than a formality, reads as the triumphant final stand rather than the hardest fight in the game, which stays Mission 35's own Cradle siege.

**The campaign is complete.** All 36 missions built, sim-tuned, tested, delivered as of this mission. See `act3_overview.md` and the campaign-wide "Still open" list in `../README.md`.

**Open finding, first surfaced 28 Aug 2026, reconfirmed 28 Aug 2026 (overnight pass) — this mission's batch win rate genuinely won't hold still, and it isn't explained by anything found so far.** The Weapon Branch balance check (`Bloom_Wars_Weapon_Branch_Mission_Balance_Check_v1.md`) ran four independent large-sample batches of the identical current-code, current-squad, no-branches configuration and got 29%, 40%, 51%, and 73% — spread far wider than sampling noise should produce at N=40-100. That check explicitly ruled out weapon branches as the cause (no separable branches-on-vs-off signal) and left it as its own open item, not folded into the branch question.

Re-checked tonight against both the pre-fix baseline sandbox and the sandbox with the new Player AI commander/Munti protection fix (`engine_systems/player_ai_engine.md`), three fresh N=40 batches: **baseline 68%, fixed-sandbox 63% and 65%.** All three land inside the same 29-73% spread the branch check already found, and the commander-protection fix moved this mission by only a few points either way — consistent with the fix's own README note that this archetype's on-hit effect (knockback) carries no damage, so there's no reason it would interact strongly with front-line caution. **That rules out two candidate explanations** (weapon branches, and now the commander-protection fix) **without finding the real one.**

What's confirmed: the instability is real (repeated batches disagree by 40+ points), it predates and survives both changes tested against it, and this file's own original tuning note already called the shipped counts (39 total, split 12/5/5/8/7/2) "the narrow middle that landed correctly" between a 0/20 wipe and a 20/20 win at nearby total-count values — i.e., this mission was already known to sit on a genuine knife-edge before either of tonight's or the branch check's passes. The leading unproven hypothesis is that a mission this close to its own tipping point is unusually sensitive to something in the Player AI's minor run-to-run nondeterminism (tile-scoring ties broken by iteration order, etc.) rather than to any single mechanic — but that's a guess, not a diagnosis; nothing here traces the actual variance to a specific cause the way the commander-protection root-cause work did for Missions 8/12. **Needs its own dedicated investigation** (start with a seeded harness so identical inputs are reproducible, then bisect what specifically differs between a 29%-batch and a 73%-batch run) before anyone treats this mission's win rate as a trustworthy number — flagged here as still open, not fixed.

**Update, 28 Aug 2026 (same night, right after the Munti repair-range fix) — the instability looks like it may actually be explained now, though not with full certainty.** The repair-range diagnostic sweep (`engine_systems/player_ai_engine.md`) happened to include this mission and came back 19/20 (95%), well outside the whole 29-73% spread above — flagged there as a standout rather than assumed. Maxime asked for another batch job to check it wasn't a fluke: three fresh, independent N=40 batches landed **90%, 100%, 98%** — plus a second full-campaign N=20 re-sweep landed **20/20 (100%)** on this mission specifically. Five independent batches, 160 trials total, 154 wins (96%), tightly clustered — nothing like the old 40-point spread.

**Leading read, not proven:** this mission is a 16-turn attrition fight, and the repair-range change bundled two things — the range bump itself (1→3 tiles) and a real bug fix (both `getRepairableFrom` and the test AI's own repair search were hardcoded to adjacent-only, so healing was far more crippled than the shipped numbers assumed). In a long survive fight, healing throughput compounds every turn; if the old adjacent-only AI's ability to actually land a heal was mostly down to incidental positioning, that would produce exactly this kind of wide run-to-run swing — and once healing reliably works at real range, that positional lottery stops mattering, which would explain the sudden convergence to a consistently high number. **Can't cleanly separate "more range" from "the bug fix" as the cause** — both landed in the same pass — and this is still an unseeded batch read, not the dedicated seeded-harness investigation this file called for above.

**Resolved for real, 28 Aug 2026 (same night) — the dedicated seeded-harness investigation this file asked for above, run in full.** Confirmed by grep first, not assumed: the ONLY randomness source anywhere in a Mission battle sim is `engine/mission.ts`'s Meeps dodge roll (`Math.random() < MEEPS_DODGE_CHANCE`) — combat damage, turn order, and every Player AI decision are all fully deterministic given a fixed unit/map state. That means swapping in a seeded PRNG (mulberry32) for `Math.random` makes an entire mission run exactly reproducible, closing the file's own leading hypothesis for good.

**Part 1, determinism check:** 5 seeds, 3 repeat runs each. All 15 runs matched their own seed's outcome AND exact turn count perfectly — **confirmed deterministic, zero hidden nondeterminism.** This directly rules out the "tile-scoring ties broken by iteration order" guess above: `Map`/array iteration in this engine is insertion-order-stable, and with the sole RNG source pinned, nothing is left to vary.

**Part 2, win rate across 100 distinct seeds (0-99), fully reproducible by anyone re-running the same script:** **99/100 (99%).** One loss, seed 92, traced turn by turn: the hostile AI's own targeting concentrated six separate attacks onto Rourke (the commander) in the very first hostile phase — five Crawlmass hits plus one Splitfang hit, 120 combined damage before any Munti had taken a single action — and she went down on turn 2, before the mission's healers ever got a turn to matter. **This is not a new problem or a coincidence — it's the exact same, already-diagnosed ceiling documented in `engine_systems/player_ai_engine.md`'s "Known, un-fixed limitations": no genuinely predictive threat avoidance, so a same-turn alpha-strike that lands before any reactive caution can fire is still possible.** It was always possible here too; it just never surfaced in the old wildly-unstable batches because something else was dominating the numbers.

**So, put together: the mission-wide instability is resolved (99% across 100 reproducible seeds, versus the old 29-73% spread), the sim itself was never actually nondeterministic, and the one residual failure mode is a known, already-documented, already out-of-scope limitation shared with Missions 8/12 — not a new mystery.** Genuinely still can't say with certainty whether the *original* 27-28 Aug instability was caused by the repair-range bump, the two dead-code bugs the same pass fixed, or some combination — all three shipped together — but the current, post-fix state is no longer a mystery at all.

**Worth Maxime's own attention regardless of cause:** a real, near-guaranteed win rate on the campaign finale is a different pacing question than the genuinely tense "harder than a formality" fight this file originally described (above) — and unlike the old instability, this number is now trustworthy enough to actually make that call from. Not re-tuned here; flagging it rather than touching enemy counts on my own read.
