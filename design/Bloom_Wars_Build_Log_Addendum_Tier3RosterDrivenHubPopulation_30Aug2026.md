## Addendum, 30 Aug 2026: Tier 3 — the Hub's walkable cast now comes from the real roster, not a fixed 3+5 name list

Consolidated Build Plan (29 Aug 2026), Tier 3 — Hub population driven by the real roster. Maxime: "fait tout en batch. 1 a la fois. jusqua ske tu manque de credit," confirmed "version complète" when asked how far to take it (full dynamic system for any active roster size, not just a status-gate on the existing fixed lists).

**Root cause, confirmed against the actual data flow, not assumed from the shape of the bug.** `buildNpcs()` built its entire walkable pilot cast from `NPC_SEED.map(...)` — a fixed, 26 Aug, three-entry list (Bosk, Anand, Iyari) — and its entire Mek cast from a second fixed five-entry list, `mekSeeds` (those three plus Rourke and Lask). Both predate every roster addition since: Second Lance and Third Lance integrate five pilots each (`integrateSecondLance`/`integrateThirdLance`, `engine/campaignState.ts`), the ROSTER_DEPTH bench adds more, and every rescued/recruited pilot goes through `generatePilot`, which writes a real, "active"-status entry into `campaignState.pilots` and a real Mek into `campaignState.meks` — the same live records `ensureHubSocialState`/`campaignState.meks` already read from elsewhere in this file. None of that ever reached `buildNpcs()`'s own source list. Traced `createWardenCampaignState` (what a fresh campaign and every existing save actually run through) to confirm all five WARDEN_PILOTS, not just the three NPC_SEED names, are "active" in `campaignState.pilots` from the very start — so Lask specifically has had a Mek in the Workshop since Meks shipped (29 Aug) but was never once a walkable pilot NPC himself, a real, immediately-visible gap this pass closes as a side effect, not a hypothetical.

**The fix.** `buildNpcs()`'s pilot loop now iterates `Object.keys(campaignState.pilots)` filtered to `status === "active"`, minus `pilot_rourke` (the player's own avatar — `this.player`, never a walkable NPC, and never in NPC_SEED for the same reason already). The three NPC_SEED pilots are matched by id (`namedSeed`) and keep their exact hand-authored seat position and starting favorability/stress/morale, unchanged — a real content choice, not something this pass had reason to touch. Everyone else gets: a pilot lookup through `findPilot` (`pilotRegistry.ts`, indexing all five roster sources) instead of the old `WARDEN_PILOTS.find`, which only ever covered one of them and would have silently shown a bare pilot id for anyone outside it; a catalyst from `catalystForPilot` (already built 28 Aug for exactly this "every possible pilot needs one" gap, previously imported nowhere in this file); the same generic `{favorability: 0, stress: 10, morale: 70}` starting point the Mek loop already established for "no hand-authored row exists yet"; and a spot picked from a real room via new `pickInitialNpcSpot` — reads live off `this.npcs` for rejection-sampled collision avoidance, the exact same jitter-and-reject shape `pickPointNearDoor` already uses for door placements (Tier 1/2's own work this session), applied a third way. Rooms are drawn from `Object.keys(ROOM_TITLES)` — the same full eight-room list `pickExploreTarget` already treats as real — so a freshly-populated crew reads as scattered across the ship, not all dumped in the rec room waiting for roaming to slowly spread them out.

The Mek side gets the identical treatment, one level down: `mekSeeds`' five hand-picked entries are untouched, and a second loop covers every other active pilot's own Mek (`pilotEntry.pilot.mekId`, a required field on every `PilotRecord` — confirmed, not assumed), landing them in the Workshop (thematically their maintenance bay, unlike pilots who scatter ship-wide) with the same generic social defaults and a `catalystForPilot(mekId)` pick independent of their pilot's own catalyst.

**Verification.** `npm run typecheck`, full `npm test` (1139/1139, zero regressions), and the full `npm run lint` (spoiler stage included), all clean. Traced the actual production data path rather than assuming it: `createWardenCampaignState` → `WARDEN_PILOTS` (confirms all 5 starting pilots, including the 3 NPC_SEED names, are genuinely "active" from a fresh campaign) → `generatePilot`/`integrateSecondLance`/`integrateThirdLance` (confirms every other way a pilot enters the roster also sets `status: "active"`, so `Object.keys(campaignState.pilots)` really is the complete, correct source of truth with no gap). Same caveat as every Hub.ts pass this session: this is logic-traced against the real code paths and data flow, not the live Playwright walkthrough the plan calls for — the walkable-cast count and spread across rooms specifically would benefit from an actual look at a mid-campaign save (15-20 active pilots) once that pass happens.
