## Addendum, 30 Aug 2026: Tier 0 — class-triangle-aware Player AI target selection, and the batch-sim harness that caught a real regression before it shipped

Consolidated Build Plan (29 Aug 2026), Tier 0, first line item: "the bot has no class-triangle awareness when targeting... the highest-leverage single fix on this whole list." Maxime: "fait tout en batch. 1 a la fois. jusqua ske tu manque de credit" — working the plan tier by tier, this is Tier 0's own opening item.

**Root cause, confirmed against the actual files, not the plan doc's own description of it.** `data/combatTables.ts`'s `POWER` matrix already IS the class triangle (`meeps->reeps: 75`, `tank->meeps: 65`, `reeps->tank: 70` — the exact three matchups the plan names) and `engine/combat.ts`'s `resolveMechAttack` already runs every real hit through it — the per-attack damage math was never the gap. The gap was entirely in target *selection*: `src/sim/playerAi/combat.ts`'s `weakestTarget` (which both `focusFireTargetInRange`'s in-range squad choice and `index.ts`'s two cross-map "which enemy do I chase" calls reduce over) ranked purely on `currentHp * effectiveDefense` — a property of the target alone, with zero notion of who's actually fighting it. A squad would converge on whichever enemy looked toughest by raw stats even when every unit in range did far more damage to a different target standing right next to it.

**The fix reuses the existing table rather than inventing a new one** (Reuse over rebuild) — `combat.ts` gained `livingSameSideMechs` (every living, path-bearing unit on the acting unit's side) and `squadAveragePowerAgainst`/`targetPriorityScore`, which divide a target's raw toughness by the squad's average `POWER[attacker.path][defender.path]` against it before ranking. `weakestTarget` takes an optional `allies` list (default `[]`, which reproduces the old unweighted behavior exactly — nothing that doesn't opt in changes). Bloom targets (no `path` — GDD §8.2, they aren't in the triangle) fall straight through unweighted regardless.

**Where it actually landed is narrower than the first pass, on real evidence, not caution for its own sake.** First cut wired the allies list into all three `weakestTarget` call sites — the in-range focus-fire choice AND both cross-map chase-target picks. Nothing in unit tests or typecheck caught a problem (1139/1139 tests, clean build) because none of them exercise campaign-scale win rates. Building a batch harness to actually check that (see below) surfaced a real regression: 400 runs across all 40 missions (36 Amaranth + the original 4) came back **67% aggregate win vs. a 73.25% baseline** — worse, not better. Root cause, traced rather than guessed: `weakestTarget(enemies)` picking which *distant* enemy to walk toward has no distance or exposure term at all, before or after this change — weighting it toward type advantage means the squad will now sometimes beeline a farther, more dangerous target purely for the matchup, the exact kind of blind aggression a real player wouldn't choose. Narrowing the fix to `focusFireTargetInRange` only — the squad's shared choice among targets *already reachable this turn*, where there's no extra travel/exposure cost to weigh against the matchup — recovered it: the same 400-run batch came back **73.5%, flat against baseline**, while still measurably improving the two mech-duel missions this item exists for (Mission 6 "House Colors": 82% -> 92% at n=50; Mission 20 "Marrow's Line" moved the other way, 98% -> 92% at n=50, likely noise given it's mostly a 1-hostile duel with little for target *selection* to even affect, but left honestly reported rather than rounded off). `index.ts`'s two chase-target call sites are left calling `weakestTarget(enemies)` with no allies list, on purpose, with a comment at both sites carrying this exact finding so a future pass doesn't quietly "complete" the fix back into the regression.

**New, permanent tool this pass needed and didn't have.** `npm run sim` (`src/sim/run.ts`) only ever runs one mission once — real evidence about a win *rate* needs many samples (`MEEPS_DODGE_CHANCE` and the Bloom on-hit-effects engine both roll genuine randomness), which is exactly what caught the regression above and exactly what Tier 0's own text asks for ("re-run npm run sim across all 36... treat the whole campaign's sim baseline as provisional until it's re-run post-fix"). New `src/sim/runBatch.ts` / `npm run sim:batch -- <N> [mission ids...]`, same per-unit action loop as `run.ts`, run N times per mission, tallied by outcome (win/loss/commander_down/timeout) with an aggregate line across however many missions were scoped. This is now the standing way to get a real baseline, not a one-off script — worth reaching for again the next time Tier 0's own "re-run the whole campaign once Player AI changes" instruction applies, including the rest of Tier 0 itself (the plan's own scope for this item goes further than this one fix — see "Still open" below).

**Verification environment**, same shape as the CommanderDown addendum's own note (this session has no `device_bash`): staged the full repo (every `src/` file, `package.json`/`package-lock.json`, `tsconfig.json`, `eslint.config.js`, `tools/lint-spoiler.mjs`) into this session's cloud sandbox via the device bridge, `npm install` there. All four gates clean on the final, narrowed version: `npm run typecheck`, `npm test` (1139/1139, zero regressions — no test in the suite exercises campaign-scale win rate, which is exactly why the batch harness above was necessary on top of them, not instead of them), `npm run lint` (spoiler-lock check itself skips without `BW_RESERVED_TERM` set, same as it does on any sandbox run — expected, not a gap), and the new `npm run sim:batch` itself as the actual balance verification for this specific change.

### Still open

This is one fix, not the whole of Tier 0. The plan's own text for this item also calls for re-running the full 36-mission sim baseline generally (not just this one change) once Player AI work is actually "picked up for real," since several of the specific numbers that prompted this tier (Mission 9's turtle-strategy read, the Mission 3/5 0%-bot results, Mission 20's own known blind-spot workaround) were tuned against the pre-fix bot — `npm run sim:batch` is now the tool for that, not yet run as its own dedicated pass beyond this fix's own verification. Missions 3 and 5 specifically are confirmed **still** at ~0% post-fix (this was never expected to touch them — `player_ai_engine.md`'s own "not a difficulty oracle" limitation is a different, deeper gap than target selection). Tiers 1 through 6 and the House Amaranth track are entirely untouched by this pass.
